# 会话迁移与网关压缩特性设计

状态：已实现，作为后续需求与代码同步的基准文档。

## 1. 背景与目标

迁移和网关压缩都会创建一个承接历史的新会话，同时保留原会话。只打开新会话或短暂提示成功，会让用户稍后回到原会话时分不清它为什么停止、历史是否被改写、接下来应该在哪里继续。

本特性解决三个问题：

1. 让用户在原对话记录中直接看到发生了什么。
2. 明确区分“已创建”“已发送”“等待目标”“结果不明”和“已完成”，不把中间状态误报为成功。
3. 保证提示可持久化、重试不重复，并且不会污染后续模型上下文。

成功时，源会话必须出现以“会话迁移已完成”或“网关压缩已完成”开头的状态记录，而不是只显示“已创建”或“已发送”。

## 2. 术语与范围

- **源会话**：用户发起迁移或压缩的原对话，历史保持可读、内容不被改写。
- **目标会话**：接收转录的新会话；迁移可跨 Agent，网关压缩在同一 Agent 内创建。
- **迁移**：把选定范围的源会话历史转录到另一个 Agent 的新会话。
- **网关压缩**：复用迁移链路，在同一 Agent 的新会话中承接选定范围的历史。
- **原生压缩**：调用 Agent 自身的上下文压缩能力，不经过本文的新会话转录流程，也不写本文的源会话提示。
- **网关提示记录**：由网关持久化并叠加到源会话时间线的状态行，不是用户或助手消息。

本文覆盖详情页和斜杠命令发起的迁移、普通会话的网关压缩，以及团队主控压缩后的换绑行为。

## 3. 总体产品契约

1. 源会话始终保持原样；操作不会截断、删除或向源 Agent 注入一条伪造的用户消息。
2. 目标会话只收到选定范围的转录和用户可选的后续指示。
3. 准备目标、创建空会话、保存正文都不等于迁移或压缩完成。
4. 只有目标转录提交成功并且账本持久化成功后，源会话才显示“已完成”。
5. 同一请求标识只创建并发送一次，也只产生一条源会话提示。
6. 发送结果不明时必须保持谨慎，不自动重复发送，也不显示“已完成”。
7. 提示记录独立于 Agent 原生历史，网关重启和页面刷新后仍能恢复。
8. 后续再次迁移或压缩时，既有网关提示不得进入模型转录。

## 4. 会话迁移：逐步行为

| 步骤 | 用户操作或系统状态 | 网关行为 | 可见结果 |
| --- | --- | --- | --- |
| 1. 打开源会话 | 查看迁移入口 | 读取可用历史与 Agent 列表；历史未就绪时禁用操作 | 目标列表不包含当前 Agent；当前 Agent 的同类操作归入网关压缩 |
| 2. 选择目标 | 选择另一个 Agent | 仅确定目标类型，不发送源历史 | 进入复制范围选择 |
| 3. 选择范围 | 选择完全复制、主要历史或最新问答 | 校验范围并生成唯一请求标识 | 进入目标设置准备阶段 |
| 4. 准备目标 | 等待模型目录 | ACP 创建或复用空目标会话后读取目录；Codex 直接读取目录，此阶段不创建聊天 | 尚未发送转录，源会话没有成功提示 |
| 5. 调整设置 | 选择模型、思考强度，可填写后续指示 | 保留准备阶段的目标会话与请求标识 | 返回上一步会放弃尚未发送的 ACP 空目标会话 |
| 6. 确认迁移 | 点击开始迁移或执行迁移命令 | 校验源会话、目标项目、标题和请求内容；通过创建账本认领请求并创建目标会话 | 控制区保持忙碌，防止重复提交 |
| 7. 保存操作 | 目标会话已存在 | 保存转录正文、目标设置及源会话提示草稿；提示草稿此时不可见 | 目标可能显示已创建或等待接管，源会话仍不显示完成 |
| 8. 提交转录 | 设置应用成功，目标可写 | 原子标记开始发送，再向目标提交转录 | 失败按“提交前失败”或“提交后结果不明”处理，见第 9 节 |
| 9. 完成 | 目标接受提交，账本写入成功 | 标记 `sent`，使源会话提示生效，并刷新相关时间线 | 源会话新增“会话迁移已完成…”，前端打开目标会话继续工作 |

如果准备阶段取消、模型设置被拒绝或目标尚未连接，流程停在相应中间状态，不得补写成功提示。

## 5. 网关压缩：逐步行为

网关压缩复用第 4 节的第 3 至第 9 步，但有以下差异：

1. 用户在压缩面板选择“网关压缩”，或通过当前 Agent 的迁移命令进入；不需要选择另一个 Agent。
2. 目标类型与源会话相同，操作类型固定为 `compact`。
3. 选择复制范围并填写可选后续指示后，创建同 Agent 的新会话并提交转录。
4. 普通会话不需要源会话保持可写连接；只读或离线历史只要已加载完整，也可进行转录压缩。
5. 成功后源会话显示“网关压缩已完成…”，不能显示成跨 Agent 的“会话迁移已完成”。
6. 新会话承接后续工作，源会话仍保留完整历史，不执行原生上下文截断。

原生压缩是另一条链路：它要求源会话已连接、可写且空闲，由 Agent 自己处理上下文，不创建转录目标会话，因此不适用本文的成功记录格式。

## 6. 状态与界面反馈

| 内部状态 | 含义 | 目标会话反馈 | 源会话成功记录 |
| --- | --- | --- | --- |
| `prepared` | 空目标已准备，尚未确认发送 | 可继续选择设置 | 无 |
| `created` | 目标和正文已保存，尚未提交 | 显示尚未发送 | 无 |
| `waiting_for_target` | 等待桌面接管、连接或设置重试 | 显示正文已保存及具体警告 | 无 |
| `opening` | 已请求桌面 App 打开目标 | 提示等待接管 | 无 |
| `dispatching` | 已尝试提交，结果不能确认 | 提示到目标 App 核实，禁止自动重发 | 无 |
| `sent` | 提交成功且完成状态已持久化 | 正常展示新会话 | 有，且仅一条 |

可见成功措辞统一使用“已完成”：

- 迁移：`会话迁移已完成：已迁移到 <Agent> 的新会话「<标题>」（<目标 ID>）。原会话历史保留不变，后续请在新会话继续。`
- 压缩：`网关压缩已完成：已创建新会话「<标题>」（<目标 ID>）。原会话历史保留不变，后续请在新会话继续。`

标题和目标 ID 用来辨认承接会话。“已发送”只作为内部协议状态，不应替代用户需要的完成结论。

这里的“已完成”指迁移或压缩操作完成，即目标会话已接受转录；不表示目标 Agent 已执行完后续任务。

## 7. 源会话提示记录

提示是源会话时间线末尾的网关状态行，展示要求如下：

1. 直接显示完整结论，不藏在工具调用详情或“执行过程”开关后面。
2. 迁移使用 `gatewayMigration`，压缩使用 `gatewayCompaction`，两者样式一致、文案可区分。
3. 每条提示对应一个请求标识，重复投影和重复请求不得生成重复行。
4. 多次不同操作按账本记录的操作发起时间排列；时间相同按请求标识稳定排序。
5. 刷新页面、重新打开会话、重启网关后仍应出现。
6. 旧账本没有提示字段时不回填、不猜测历史操作结果。
7. 提示语言采用操作发起时的界面语言；之后切换界面语言不重写历史提示。

提示由网关注入展示视图，不写回 Codex、ACP 或其他 Agent 的原生历史文件，因此源 Agent 不会把它当作用户指令。

## 8. 转录范围与模型上下文边界

| 范围 | 转录内容 |
| --- | --- |
| `full` 完全复制历史 | 在预算内保留完整对话与活动，优先保留首个任务、最近问答和近期记录 |
| `main` 只复制主要历史 | 默认排除例行读取、普通工具调用等噪声，保留主要问答、错误与关键摘要 |
| `latest` 只复制最新提问和结果 | 保留最后一组有效用户提问及其后的回答，忽略普通活动记录 |

共同约束：

- 转录有消息数、字符数和字节数预算；发生裁剪时必须标明。
- 图片不伪装成已迁移，使用明确的省略标记。
- 用户后续指示作为独立指令附加在转录之后。
- 所有范围都在所选历史后附上发送账本中排队中或明确发送失败的用户消息，按队列顺序复制，并标注原会话尚未发送；空历史也不能遗漏这些消息。
- 不复制已接受、取消、忽略或内部任务提交；存在用户消息发送结果待确认时拒绝新迁移，先核实原会话，避免重复执行。已完成迁移的同请求重放仍返回原结果。
- 未发送消息与历史共享转录预算，裁剪必须标明；附件只保留名称和未迁移标记，不把上传 ID、路径或源 Agent 的 Skill/权限配置当成目标可用资源。
- 这是内容复制，源会话的发送账本不被修改；原队列仍可在原会话继续派发，界面需说明队列保留，用户在目标会话继续时应自行处理原队列。
- `gatewayMigration` 和 `gatewayCompaction` 提示在所有范围中都被排除。
- 目标会话可保存 `forkedFrom` 来源链接，但该链接不等于把源会话改成只读。

## 9. 异常、重试与并发

1. **历史未就绪**：拒绝发起，提示等待历史加载，不创建目标。
2. **准备阶段取消**：仅放弃已准备且未发送的空目标；正在确认发送时不得放弃目标。
3. **模型或思考强度无效**：停止发送，保留设置页供用户重新选择，不写源会话成功提示。
4. **目标创建结果不明**：保留无目标 ID 的账本认领，要求先核实，避免重复创建。
5. **目标未连接**：保存正文和提示草稿，返回等待目标；连接后可沿原请求重试。
6. **提交前明确失败**：回到可重试状态，不显示完成。
7. **提交后结果不明**：保留 `dispatching`，不自动重试、不显示完成，由用户到目标 App 核实。
8. **成功响应重放**：返回已记录结果，不再次创建、不再次提交、不重复提示。
   正文保存后，延迟重试始终使用该正文快照；源队列后续编辑或状态改变不会替换已保存的转录。
9. **同一请求标识内容不同**：拒绝复用，防止一个请求被改成另一个目标或项目。
10. **完成状态落盘失败**：接口报告失败；不得让界面仅凭内存状态宣称持久化完成。
11. **源消息结果待确认**：在创建或提交新的迁移目标前拒绝，不把可能已执行的用户消息再次作为任务带到目标。

Codex 延迟重试也必须使用账本中已保存的源会话提示；不能在等待桌面接管后的另一条发送路径上漏记。

## 10. 团队主控的附加行为

团队主控执行网关压缩时，除普通会话规则外还必须满足：

1. 请求携带团队标识和主控维护标记，网关核对当前主控绑定。
2. 存在未结束 Run 时拒绝压缩，要求先结束或取消。
3. 存在待路由或等待处理的 TeamInput 时拒绝压缩。
4. 新会话创建后、正式换绑前再次检查主控绑定，避免覆盖期间发生的变更。
5. 只有压缩成功后，才把团队主控换绑到新会话并继承旧主控设置。
6. 源会话的“网关压缩已完成”仅表示转录新会话已创建，不代表团队换绑成功；换绑失败必须由团队界面另行报告。
7. 团队压缩不应额外创建团队 Run。

## 11. 技术实现映射

- [创建账本](../internal/httpd/creations.go)：保存 `sourceId`、`sourceNotice`、`sourceOperation`；提示草稿与发送状态分开持久化，仅 `sent` 条目对源会话可见。
- [迁移入口与提示生成](../internal/httpd/migrate.go)：处理准备、创建、延迟发送、重试和成功落盘；构造本地化提示，并从后续转录中排除网关提示。
- [ACP 与 Codex 视图](../internal/httpd/server_bridge.go)：把账本提示叠加到在线及离线源会话视图。
- [实时投影](../internal/httpd/live_projection.go)：把提示纳入元数据版本，操作成功后触发时间线更新，并生成稳定的 `gateway-maintenance:<request-id>` 轮次。
- [前端时间线](../web/timeline.js)：以始终可见的状态行展示提示，不受“执行过程”显示开关影响。
- [迁移与压缩控件](../web/migrate.js)：维护准备、确认、忙碌和取消语义；请求标识贯穿重试。
- [应用流程](../web/app.js)：区分迁移、网关压缩、原生压缩，并在团队场景执行主控换绑。

提示记录只包含操作类型、目标标题和目标 ID，不通过状态元数据暴露完整转录正文。

## 12. 验收标准与测试

每次修改相关行为，至少按受影响范围核对以下场景：

- [ ] 跨 Agent 迁移成功，源会话只有一条“会话迁移已完成”记录，包含目标 Agent、标题和 ID。
- [ ] 同 Agent 网关压缩成功，源会话只有一条“网关压缩已完成”记录。
- [ ] 同一请求重试不重复创建目标、不重复发送转录、不重复追加提示。
- [ ] 准备、等待目标、发送结果不明和设置失败时均没有成功提示。
- [ ] Codex 等待接管后通过延迟路径成功，提示仍能恢复。
- [ ] 页面刷新、离线历史读取和账本重载后提示仍存在。
- [ ] 关闭“执行过程”后提示仍可见。
- [ ] 再次迁移或压缩时，旧提示不进入新会话的模型转录。
- [ ] 空历史仍复制失败和排队用户消息；所有范围按队列顺序复制，已接受/取消/忽略及内部提交不重复进入转录。
- [ ] 未发送消息的附件明确标记未迁移；结果待确认阻止新操作，但已完成请求重放不再次发送。
- [ ] 转录包含未发送消息时仍遵守预算并标记裁剪，复制不会改动源队列账本。
- [ ] 团队有活跃 Run 或待处理输入时无法压缩，成功后才执行主控换绑。
- [ ] 中英文操作分别生成对应语言的历史提示。

标准验证命令：

```sh
make test
node --test tests/test_*.js
go vet ./internal/httpd
```

相关回归测试位于 [迁移后端测试](../internal/httpd/migrate_test.go)、[状态持久化测试](../internal/httpd/migration_state_test.go)、[迁移前端测试](../tests/test_migrate.js) 和 [时间线测试](../tests/test_timeline.js)。

## 13. 文档与代码同步流程

本文是迁移与网关压缩特性的需求基准。后续新增或调整需求时按以下顺序执行：

1. **先改文档**：写明用户目标、逐步行为、界面措辞、异常结果和验收标准；有歧义先确认，不直接用代码猜测产品语义。
2. **评审差异**：区分新增需求与当前已实现行为，标明受影响的状态、数据契约和兼容策略。
3. **再实现代码**：按文档实施，并同步更新覆盖该行为的测试。
4. **完成时回写**：若实现过程中确认了新约束，立即补充本文；不得留下代码已变而文档仍描述旧行为的状态。
5. **验证后交付**：运行第 12 节相关检查，并说明实际验证结果及仍需重启网关等部署条件。

仅修错字且不改变行为时可直接修订文档；任何可见行为、状态含义、接口字段或持久化语义变化，都必须先经过上述文档先行流程。
