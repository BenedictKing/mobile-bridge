## 1. 目标与取舍

把团队演进为“用户定义目标和边界，系统围绕可核验产物持续推进”的工作方式。用户主要处理目标取舍、真实授权和无法机械判断的结果；Lead 负责提案，网关负责确定性调度、证据校验和资源约束。

核心执行链：**原始目标 → 验收契约 → 任务图 → 独立产物 → 独立评测与审查 → 集成验证 → 目标判定**。失败回到具体条件和责任任务，避免整个团队重复讨论或重做。

| 摘录中的思路 | 本项目采用的机制 | 明确的限制 |
| --- | --- | --- |
| 定义奖励与 Evals | 先固定完成条件、检查方法、版本和预算 | 不用模型自评分签发成功 |
| 把问题变得可验证 | 将模糊目标分解为行为检查和人工判断项 | 测试代理指标不能覆盖全部体验与业务价值 |
| 主会话协调蜂群 | Team Chat 持续接收输入，Lead 提案，网关执行 DAG | 不另建 Agent runtime 或第二套调度器 |
| 独立工人并行 | 独立执行上下文、工作区和产物身份 | 文件不重叠不代表接口、数据与依赖互不影响 |
| 专门模型找问题 | 未参与实现的 Reviewer 检查同一候选版本 | 更大模型或多数票不天然更可信 |
| 公共看板 | 可追溯的任务通信、决策和证据引用 | 可审计不等于能证明不存在模型串通 |

首版面向现有小团队；建议从两个并行实现槽位起步，并受现有更低限额约束。不以“几十个 Agent”作为验收目标，也不同时展开大量候选方案。咨询、单点修改保留短流程，只有存在独立产物时才拆分。

设计阶段不改变运行时。实现阶段继续遵守仓库权限约定；用户接受契约不自动授权推送、删除、改写历史或生产操作。

## 3. 架构与职责

沿用 `Issue → GoalContract → Run → Task → ExecutionThread → ProviderSession`。Swarm 是 Team 的可选执行策略，Issue 继续作为用户工作对象。阶段从 Task 和证据折叠，不维护第二份阶段状态机。

```text
用户 / Team Chat → 目标与约束 → Lead 规划提案
                                  ↓
                         网关校验 / 预算 / DAG
                                  ↓
                  Worker A                 Worker B
                     ↓                        ↓
                  候选产物 A               候选产物 B
                     ↓                        ↓
               独立 Eval / Review      独立 Eval / Review
                     └───────────┬────────────┘
                          集成候选 + 整体验证
                                  ↓
                          目标判定 / 用户确认
失败证据 → 有限修复任务 → 新产物版本 → 重评受影响条件
全部业务决策与结果 → 既有 journal → 事项看板与事件流
```

| 角色或组件 | 职责 | 不能自行决定 |
| --- | --- | --- |
| 用户 | 原始目标、业务取舍、必要授权、语义确认 | 用户认可不能覆盖机器检查失败 |
| Lead | 拆分任务、建议条件、配置检查、归因与调整方案 | 删除原要求、降低门槛、修改检查结果 |
| Worker | 在契约内产出改动，自检并提交证据线索 | 签发自身最终验收、扩大写入边界 |
| Eval Runner | 在绑定环境运行冻结检查并记录客观结果 | 按模型文字推测命令退出码或测试通过 |
| Reviewer | 独立审查条件覆盖、缺陷与反例，给出可定位 findings | 修改候选产物、替用户豁免必要条件 |
| Integrator | 组合已通过的产物，处理接口与集成冲突 | 自动修改用户主分支或把分支通过视作整体通过 |
| Gateway | 策略、租约、派发、证据有效性、目标投影与恢复 | 以调度完成数替代目标达成 |

这些是职责，不要求每项都有一个常驻模型。确定性检查由程序执行；集成无冲突时不调用模型；Lead 仅在规划、异常归因、修订和收口时介入。现有服务通过小型端口扩展评测与产物处理，避免复制队列、锁、审批及恢复逻辑。

## 4. 目标契约与评测规格

扩展既有 `GoalContract/GoalCriterion`，不另建一套需求清单。Lead 先提出条件和评测建议；网关保留完整原话、来源区间、约束与修订，并检查覆盖关系。文字覆盖完整只能证明未丢原文，不能证明语义翻译正确。

| 对象 | 保留与扩展的信息 |
| --- | --- |
| GoalContract | 复用 `Revision`（请求仍用 `goalRevision`）；关联来源及 scope 哈希，新增接受主体和策略版本 |
| GoalCriterion | 稳定 ID、原文引用、可观察结果、`checkKind`、必要性、证据引用 |
| EvalSpec | ID/revision、criterionIds、执行器、固定 argv、工作区选择、输入/环境、阈值、超时、资源上限 |

`checkKind` 分为 deterministic、review、human；一个条件可以组合多种检查。示例：

| 原始要求 | 可核验部分 | 剩余判断 |
| --- | --- | --- |
| 队列重启不丢任务 | 故障注入后输入可恢复；派发身份不重复；未知发送不重试 | 是否覆盖用户的真实部署方式 |
| 手机交互顺手 | 390px 无横向溢出、关键动作可达、键盘焦点正确、错误可恢复 | 真实使用体验由用户确认 |
| 并发延迟达标 | 固定设备、数据、并发数、预热与样本量，比较规定分位数 | 场景是否代表业务，由契约定义者判断 |
| 解析准确 | 固定标注集与版本，分别统计漏报、误报及各类边界 | 数据集代表性与标注争议不能交给实现者自证 |

执行前的规则：

1. 系统使用用户明确的阈值或已接受的项目模板生成确定性条件；Lead 新提的模糊业务条件保留建议身份。可继续已授权工作，不必为每个技术细节阻塞；该条件最终仍走人工判断。
2. 已接受的契约及 EvalSpec 按版本冻结，绑定计划哈希和派发输入。Worker 可以增加测试，不能修改受保护的验收规格、基准数据、阈值或将失败用例移出检查。
3. 目标新增形成修订；降低门槛、删除条件或豁免 required 检查必须由有权用户显式决定并保留旧契约。Lead 以“紧急”“代价太高”为由自行豁免无效。
4. 需求本身无法机械判断时明确 human 条件，不能通过堆积测试数量宣称已解决。没有合理验证方法的事项可以继续调查，但不得自动成为 satisfied。
5. 首版自动化只产出客观证据和逐项建议，保留现行用户确认。后续仅对已授权的、全部确定性且覆盖完整的契约允许机械判定 met；任何人类判断项继续 pending_confirmation。

规格采用固定 schema 与已注册执行器，不提供任意表达式语言。命令路径、参数和解析器身份属于规格；模板升级不改变已运行实例，结果未知或缺字段不能回退为成功。

## 5. 任务拆分与依赖契约

Task 的粒度由“一个可独立验收的产物”决定，不按文件数或固定时长机械切分。任务能说明输入、输出、失败条件、复验方法和交接对象，才适合派发。只读调研、计划及汇总用符合其目的的证据要求，不强制代码测试。

每个实现任务附结构化契约，扩展现有 Task/Plan 输入：

```yaml
taskId: queue_api
issueIds: [queue_reliability]
criterionIds: [durable_input, no_duplicate_dispatch]
phase: implement
dependsOn: [accepted_plan]
inputArtifacts: [queue_interface_v1]
allowedWritePaths: [internal/team/, internal/httpd/team_inputs_queue.go]
protectedPaths: [acceptance/queue/, acceptance/eval-specs.json]
output: patch_and_behavior_report
evalSpecIds: [queue_recovery_v1]
workspaceId: worker_api
reviewPolicy: required
```

以上为目标 schema 示例，不是当前可提交 API。`inputArtifacts` 必须携带生产者、内容身份和契约版本；字符串别名仅用于阅读。`criterionIds` 必须能追溯到有效目标，不能只给任务一个“完成标准”自然语言段落。

派发门禁扩展现有 DAG 校验：

- **完整**：原始要求与约束有归属，必要条件有负责产物和检查；未知归属明确待处理。无来源的新增需求不能悄悄进入范围。
- **可组合**：先冻结接口、错误语义、数据格式与配置约定；下游依赖经过验收的产物版本，不能只依赖上游 Task.completed。
- **可并行**：共享工作区继续单写；不同 worktree 仍分析公共接口、锁文件、schema、生成物等冲突。改共享依赖时串行或先完成基础任务。
- **可追责**：每个候选有唯一生产任务和 attempt。Agent 报告的 touchedPaths 仅作线索；实际变更清单由网关采集，越界产生阻塞证据，不能自动删回用户改动。
- **可负担**：计划计入审查、评测、修复与集成成本，给必要后续步骤预留容量；资源不足时减少并发或分批，不跳过验收。

前端依赖后端接口时，可以在冻结接口后并行；接口发生变化会使依赖它的候选待重验。单 Run 容量不足时沿用已有分批/修订关联，跨批只消费已登记且验证通过的产物，不在多个 Run 间暗建第二套调度器。

## 6. 奖励函数与质量判断

这里的 Reward Function 是运行时选择与反馈规则，不涉及训练模型。Worker 自检用于快速找到问题；独立执行器和 Reviewer 产生验收证据；网关判定有效性。三者不得合并成一个模型自报分数。

采用“硬门禁 + 质量向量 + 成本约束”：

```text
eligible(candidate) =
  契约与产物版本匹配
  AND 全部 required 机器检查有效通过
  AND required 独立审查有效通过
  AND 没有越界、缺失证据或未核查副作用

goalSatisfied = 全部条件 met AND 必要人工确认已取得
质量向量 = [条件满足情况, 回归情况, 业务指标, 证据完整性]
效率记录 = [实际耗时, 派发次数, 评测消耗, 已知 token/费用]
```

`eligible` 表示候选具备进入后续集成或确认的资格，不能独立关闭事项。必要审查缺失或不可独立完成时仍不合格。不同候选只在相同契约、数据、环境和资源条件下比较；先满足硬条件，再按契约规定的指标优先级比较，等价候选优先选择成本更低、变更更小的方案。首版只保留一个主候选，不实现竞赛排行榜或多臂老虎机。

防止指标被钻空子：

| 风险 | 设计约束 |
| --- | --- |
| 增加无效测试刷覆盖率 | 覆盖率只作辅助；行为断言、负例和关键路径必须独立通过 |
| 删除用例、修改 expected、降低阈值 | 验收规格与基准受保护，变更走新版本及独立审查 |
| 优化某个延迟却牺牲正确性 | 正确性先作硬门禁，固定负载及样本量再比较延迟 |
| 重试直到偶然通过 | 每次尝试留痕；不稳定结果标为 inconclusive，按预定复测规则处理 |
| 大量拆任务制造进度或绕过限额 | 条件完成度与 Task 数量分离；同事项修订共用预算 |
| 模型声称低成本或高准确率 | 使用网关/执行器观测值；缺少 provider 用量时标记未知，不估成零 |

可用固定种子的生成测试和独立维护的保留用例提升发现缺陷的能力，但同机且无隔离时不能宣称测试数据对 Worker 保密。任何隐藏评测机制都不能替代真实需求覆盖与事后抽查。

## 7. 独立评测、审查与证据

### 7.1 评测绑定的对象

Eval Runner 接收候选快照而不是“去 Lead 目录跑一下”。一次 EvalRun 至少记录：`evalSpecId/revision`、`criterionIds`、`taskId/attempt`、`artifactId/contentHash`、`workspaceId`、基线、检查程序与数据哈希、工具链/依赖/相关配置指纹、实际 argv、起止时间、退出码、结构化指标和日志引用。敏感配置仅记录必要的非敏感身份，不写原值。

评测前取得新鲜指纹并冻结输入；在独立副本执行，构建缓存与产物写到该评测环境。评测后检查源输入未变，测试产生的合法输出单独登记。外部写入或版本不一致导致本次证据无效；仅做前后哈希比较不能防止中途改动又还原，因此自动验收须具备可信快照或实际文件系统隔离，不能只依靠提示词。

验收命令来自冻结规格，使用 argv 执行。`make` 或包管理器脚本仍能执行仓库代码，命令前缀白名单不能充当沙箱。执行器须声明超时、进程终止、资源、网络及凭据边界；读写能力未受控的本地模式只提供辅助证据，不能自动签发严格隔离的检查通过。

| 评测结果 | 含义 | 后续处理 |
| --- | --- | --- |
| passed | 检查真实执行，阈值满足，产物与环境匹配 | 形成该版本证据 |
| failed | 有效执行且断言或约定阈值不满足 | 生成具体修复建议 |
| inconclusive | 超时、环境失败、缺依赖、结果格式错误或不稳定 | 先处理环境/检查问题，不算通过或业务失败 |
| interrupted | 暂停、取消或进程中断 | 保留尝试和部分日志，不签发结论 |

证据有效性另记 `fresh/stale/unknown`，与上述执行结果正交；`stale` 不改写原来的 passed。耗时是目标指标时，超过明确性能阈值可以 failed；基础设施执行超时仍是 inconclusive。

### 7.2 独立审查

Reviewer 取得原始要求、冻结契约、精确候选 diff/快照和客观 Eval 记录；首轮不注入 Worker 的自我评分或其他 Reviewer 结论。先记录自己的裁决，再允许公开讨论及复核，以减少相互迎合。

独立性检查生产者身份、实际 ProviderSession、执行线程和工作区权限，不能只比较显示名或换一个 memberId。同一实现上下文不能做自身 required 审查；换模型并非强制，也不能代替隔离。缺少合格 Reviewer 时保留 pending_verification，用户可亲自审查或显式修订要求，Lead 不能降低要求。

审查输出扩展为 `criterionId + verdict + findings + evidenceRefs`；每个 finding 有稳定 ID、严重性、路径/行为、复现步骤和处置结果。`met` 必须引用有效证据；模型发现的语义问题可阻止推进，模型声称“没问题”不能替代实际 Eval。缺项、格式异常或没有看过候选均保持 unknown。

### 7.3 失效与完整性

内容哈希覆盖实际改动与未跟踪文件内容，HEAD 仅作出处；相同内容提交后不重验。路径级复用必须同时覆盖接口、依赖、锁文件、配置、测试与数据等依赖闭包；闭包不明确时采用完整候选树，不能仅相信 Agent 自报的 touchedPaths。最终集成始终检查完整候选。

日志可截断展示，但机器指标、退出码和产物身份须完整落账；大日志存制品并保留哈希与受认证入口。必需制品缺失或不可读取时证据变 unknown。历史确认保留其版本，新候选必须重新计算有效性，不把旧确认用于新目标。

## 8. 工作区隔离与集成

独立 worktree 解决工作副本冲突，不隔离进程权限、凭据、网络、git 公共元数据或端口。写入范围声明只是规划约束；严格模式须有适配器支持的实际限制，无法限制时明确降级并禁止无人值守验收。

首版使用用户预备、登记的 worker 和 integration 工作区。未来自动供给放在独立阶段：运行前明确展示要创建的数量、位置、基线和权限，取得仓库要求的显式授权并记录范围；不以接受设计或启用 Swarm 推导出创建/删除分支的权限。

每次派发前的 preflight：

1. 确认仓库根、工作区归属、基线与目标契约版本；记录用户已有改动。基线漂移时比对，允许且可 fast-forward 才同步；无法安全同步则停靠，不 stash、强制覆盖或重写历史。
2. 检查实际 Provider 会话 cwd 与 workspaceId 一致。不能重绑定已有活跃会话来冒充隔离；能力不足时串行或明确等待。
3. 前端任务先识别锁文件/包管理器并检查依赖，按已有授权在该 worktree 安装；本地配置按必要字段初始化，凭据不写入任务文本。依赖失败记环境原因。
4. 分配独立端口、缓存和构建目录；锁文件、schema、全局资源及共享数据库单独协调。worktree 不共享可写 node_modules，也不借用用户生产数据。
5. 建立 workspace/成员租约，核对实际 changed paths、符号链接及路径规范化；跨界写入阻止接受产物并保留证据。

集成是明确的产物步骤：

```text
固定基线 B + 已验收候选 A、C
  → 在专用集成工作区按依赖顺序组合
  → 新集成候选 I（记录输入候选及内容哈希）
  → 全树构建 / 行为 / 接口 / 必要集成审查
  → 可交付结果与证据
```

组合使用授权的候选应用操作；可在预备目录中应用补丁，不默认执行 merge/rebase/cherry-pick。必须检查候选是否已包含其他候选的输入，避免重复应用。同文件冲突、公共接口变化或基线漂移生成集成修复任务，禁止覆盖某一方或重复套补丁猜结果。

分支各自通过不能证明组合通过。集成引入的新改动需要独立检查；最终交付绑定 I 的内容身份，并列明目标是“补丁/候选可交付”“主工作区已应用”还是“已发布”。用户要求后两者时，前者只能算部分达成。

主工作区应用与推送、发布、删除 worktree 均为独立操作。推送及仓库约定的破坏性动作继续逐次显式确认；清理不得隐含于取消或回滚。已保存候选和必要证据按保留策略保存，清理不能使仍被目标引用的证据失联。

## 9. 修复闭环与停止条件

失败回路为：`有效失败证据 → finding → 责任产物/任务 → 修复提案 → 网关校验 → 新 Task/attempt → 新候选 → 复验`。只重做受影响的任务、下游和集成检查，无关分支继续推进；外部副作用未知时不得自动重发。

| 情况 | 系统动作 | 停止自动推进的条件 |
| --- | --- | --- |
| 明确的断言失败 | 附复现输入和日志，派给原责任角色 | 同一问题重复出现或修复预算耗尽 |
| 审查发现缺陷 | 新建关联 finding 的修复 Task，再独立复审 | 审查意见冲突、需求歧义、无法满足 |
| 审查格式无法解析 | 复用一次有界格式修复 | 仍 unknown，不能把格式修复计作功能修复 |
| 依赖或环境不就绪 | 在已授权范围准备环境后重新评测 | 缺凭据、网络不可达或必要能力不存在 |
| 用例不稳定 | 按冻结的复测规则采集所有样本 | 证据仍不确定，不反复运行挑选成功样本 |
| 合并候选冲突 | 生成明确集成修复任务和冲突报告 | 需要业务取舍或越过授权范围 |
| 发送或创建结果未知 | 依据既有 submission/creation 身份对账 | 无法确认，保留 outcome_unknown |

建议初始默认：每个条件最多两次自动功能修复，首次实现不计入；同一规范化失败签名连续两次出现时提前停靠。签名包括条件、检查版本、错误类型和位置等客观字段，不取模型自由改写的标题。格式修复单独计数，但所有调用都计总派发预算。

次数之外必须有总边界：沿用 Team 并发、单 Run 容量和日派发限制，新增事项执行链的修复/评测次数与墙钟期限上限。按 Issue 和契约血缘继承预算，amend 或新 Run 不能清零；共享任务的实际消耗只在 Team 总账计一次，各事项引用该消耗，不能分摊成零。增加预算需沿用用户授权策略。

留出 Reviewer、Eval 与收口资源，防止 Worker 用光全部额度后无法验证；评测进程另有资源上限，不因不调用模型就不计成本。不具备精确 token/费用数据时，以可测的次数、时间和资源额度强制封顶，未知费用保持未知。

状态沿用现有契约：Task.completed 表示一次执行结束；候选未验收不会满足依赖的产物门禁。Run 可在执行结束后保持目标 pending_verification/pending_confirmation；是否恢复在途 Run 或新建修订 Run 按既有终态规则决定，不能把终态历史改回 running。

预算、能力或证据阻塞返回具体 reasonCode、责任对象、已做工作和下一步，例如“同一回归连续两轮未消除，需调整方案”，不笼统写“等待用户”。只有影响目标取舍、真实授权、资源或无法核验事实时才通知用户。

暂停停止新派发并允许已发任务结算；取消尝试终止受控进程并保留副作用，不能自动回滚文件。旧 attempt 的迟到结果只补历史记录，不完成当前候选；恢复必须核对契约、产物、租约、剩余预算及未决外部调用。

## 10. 公共协作记录与上下文

公共看板是既有 Team journal 与任务事件的投影，作为协作事实的共同入口，不新增聊天室、消息总线或私有 Agent mailbox。记录可见于有权访问该 Team 的用户及授权角色，“公共”不表示对互联网公开。

所有通过团队系统发生的跨任务交接必须带上：发送者/接收者、issueId、runId、taskId/attempt、契约及产物版本、因果事件 ID、正文或证据引用。派发输入固定记录引用的事件游标和上下文哈希，防止事后看板变化改变历史解释。

| 记录类别 | 用途 |
| --- | --- |
| plan / assignment | 分工、依赖、写入边界、完成条件和接受理由 |
| question / answer | 接口歧义、缺失上下文、用户回答与有效范围 |
| artifact / eval | 候选内容、运行环境、真实检查结果及失败复现 |
| review / finding | 独立裁决、问题条目、修复或争议处置 |
| decision / intervention | 改计划、改阈值、预算授权、暂停与恢复 |

模型可提出记录，网关验证身份和结构后追加；模型不能直接改 journal 或伪造另一角色的发言。编辑与撤销形成新事件，原记录保留。日志、外部网页、工具输出和其他 Agent 文字均是数据，不能修改系统规则或绕过审批。

上下文按依赖取用：Worker 取得自身契约和已验收输入产物；Reviewer 取得需求、候选及客观证据；Lead 取得变更摘要、阻塞项和可追溯引用。限制注入字节数及条数，超限提供可查询引用，不向每个 Agent 广播全部 transcript。

“严禁私下串通”落为可执行边界：团队工具不提供绕过记录的跨 Agent 通道；候选评测结果只能由对应执行器记账；首次独立审查不预读其他裁决。共享本机权限或 provider 自带的外部通信不受此协议完整控制，因此不能声称已证明不存在私下通信。严格隔离依赖实际工具与网络策略。

不要求记录模型内部思维过程。记录决策理由、必要业务通信、工具动作和结果证据即可；凭据、敏感数据和不相关私人会话不进入公共上下文。角色的上下文选择与用户查看完整审计记录是两种权限，不能通过看板默认把保留评测数据再发给 Worker。

事件流复用现有持久序号、去重与补读；原始制品通过受认证引用按需读取。看板离线不影响执行事实，重新连接后按游标补齐，不从聊天文本重建任务状态。

## 11. 用户交互与完整示例

沿用 Team Chat、事项看板、任务详情与执行记录入口。Swarm 只增加契约、证据与有限自动推进能力，不要求用户维护另一张蜂群控制台。

事项详情按阅读顺序展示：目标和原话 → 当前结果 → 必要条件及证据 → 阻塞与下一步 → 任务/成本/完整记录。阶段仍由实际任务投影，执行任务数量只表示执行进度。条件尚未冻结或没有可计数条件时，不展示伪精确的达成百分比。

计划卡由系统生成，默认折叠技术细节；展示完成条件、并发、工作区、预算及需要用户判断的项。已有授权且无歧义时直接执行，不为每次内部审查、重测或阶段切换增加确认按钮。范围改变、需授权操作或不可判断条件才提供具体操作入口。

建议示例文案：

```text
队列恢复可靠性
结果待确认 · 必要检查 3/3 通过，体验条件 1 项待确认
执行：两个实现任务、一次修复和集成验证已结束
产物：集成候选 v3 · 独立审查通过
需要你处理：在手机上确认排队操作是否符合预期
[查看结果] [确认符合要求] [反馈问题]
```

“确认符合要求”只记录对该版本结果的认可；“应用到主工作区”“推送”“清理工作区”分别显示真实操作和影响，不混入验收。手机优先展示阻塞、结果和下一步，哈希、argv 和租约放到证据详情。原队列开关及立即发送、编辑、删除语义保留。

完整示例（假设用户要求“修复排队输入在重启后的丢失，并改善手机操作”）：

1. Lead 保留原要求，提出 C1 输入持久化、C2 不重复派发、C3 既有队列操作可用、C4 手机体验。C1–C3 配置确定性检查和审查，C4 保留人工确认。
2. 先固定队列 API 和错误语义。后端 Worker 在 A 工作区修改恢复；前端 Worker 在 B 工作区改提示与操作，两者只在接口固定后并行。
3. 后端自检通过，但独立故障注入发现“写入 submission 后崩溃”导致重复派发，C2 failed；系统记录 finding 并只派后端修复，前端不重做。
4. 修复形成 A2；独立评测及 Reviewer 对 A2 给出有效通过。前端 B1 通过行为与布局检查，手机主观体验仍未确认。
5. 集成 A2+B1 得到 I1。重新运行跨层队列场景、完整回归及必要审查；未验证 I1 前不能把 A2、B1 的通过合并为最终成功。
6. 用户看到 I1 的结果和 C4，确认后按契约形成目标达成。若原任务明确要求应用主工作区，必须完成该步骤及对应版本核验后才能全部达成。

反例：若真实问题只需改单个按钮文案，则用一个任务和现有低影响验证即可，不启动两个 Worker、专项 Reviewer 或多轮蜂群流程。

## 12. 数据、接口与恢复

### 12.1 最小模型与归属

| 对象 | 设计增量与持久化归属 |
| --- | --- |
| TeamPolicy | 可选 Swarm 策略、修复与评测预算、所需能力；沿用既有权限边界 |
| GoalContract/GoalCriterion | 冻结规格及条件关联；Issue 持有长期目标，Run 引用执行版本 |
| Task | 契约版本、criterionIds、输入产物、写入范围、evalSpecIds；复用 attempt/线程/租约 |
| ArtifactRef | 生产任务/attempt、基线、内容身份、实际路径清单、存储引用与输入血缘 |
| EvalRun | 独立检查尝试和证据元数据；Run journal 为执行事实，制品存储放大日志 |
| Finding | 条件、证据、责任产物、修复任务与处置记录；不自建通用工单系统 |

`GoalEvidenceRef` 扩展引用上述记录，继续生成同一个 `outcome/goalOutcomes` 投影。旧 status、Issue 和共享 Run 关系保留；没有这些字段的旧任务仍按原规则读取，不能补造通过证据。新 schema 中未知的 required 检查类型须拒绝或显示不支持，不能忽略后继续验收。

无 Issue 的显式计划沿用 Run scope，契约保存在 Run，并通过执行记录入口访问；不为启用策略强行创建事项。定时执行继承 schedule 对应的契约版本，每次触发生成独立候选与证据，不能沿用上一轮通过结论。共享 Run 的多个 scope 分别冻结并判定，共享产物引用同一份事实。

### 12.2 命令与事件方向

以下为拟议接口，尚不存在：

- `POST /api/teams/:teamId/issues/:issueId/contract-proposals`：Lead 建议或用户定义执行前契约。
- `POST .../contract-proposals/:proposalId/accept`：校验来源、范围与权限，冻结契约；接受计划不附带工作区或外部操作权限。
- 无 Issue 时在 `/api/teams/:teamId/runs/:runId/contract-proposals` 提供同一提案/接受语义，复用服务逻辑。
- `GET /api/teams/:teamId/runs/:runId/evals`：列出实际评测及证据有效性。
- `POST .../runs/:runId/evals/:evalId/recheck`：用户或授权策略请求复验，生成新 attempt，不改旧结果。

复用既有 Team 认证、乐观版本、操作 UUID 和错误语义。同 UUID 同内容返回同结果，异内容或旧版本返回冲突；Worker 不能调用契约接受、阈值变更或伪造 runner 结果接口。内部 runner 结果通过受控端口入账，不作为通用 Agent 写接口暴露。

契约接受是前置执行操作；现有 `goal-review` 的事后确认继续保留，不直接把它放宽成进行中随意改条件。接口需要贯通 Lead 提案、HTTP 校验、Plan/action、派发、快照、journal 重建和前端，避免只加内部字段却在入口丢失。

拟增事件：`contract_accepted`、`artifact_recorded`、`eval_requested/started/finished`、`finding_recorded`、`repair_scheduled`；尽量扩展已有审查及失效事件。用户决策追加版本事实，不原地编辑旧事件。

### 12.3 幂等、恢复与证据一致性

先持久化评测/修复意图和预算预留，再执行副作用。幂等键覆盖 Team/Run、契约版本、任务 attempt、候选内容、EvalSpec 版本与评测 attempt；合法重测使用新 attempt，网络重试沿用同一操作键。完成结果先落 journal 再更新投影和释放产物依赖。

Issue 契约为长期权威版本；Run 保存冻结引用及执行事实，Issue 的执行摘要由此投影。同一操作先记唯一接受意图，再幂等写入关联记录并标记完成；两份现有账本之间不能假设跨文件事务。任何缺失链接先对账，未完成接受的契约不允许派发。

重启对账 runner 的持久 operationId、实际进程身份及制品，再结算同一次尝试；只有确认旧执行已结束且检查可安全重跑时才产生新 attempt。失去进程控制、外部检查有不明副作用时停靠核查，不默认重跑命令。制品缺失、契约变化、成员换绑、工作区消失均保留原因，不能拿当前会话或目录替代历史归属。

隔离能力按 provider/执行器声明并在 preflight 验证：可创建会话、可靠指定 cwd、可取消、能否限制写路径及网络、可取得结果与用量。未知能力视作不满足严格模式，不改 Provider 审批模式来强行通过。

## 13. 分阶段实施、验证与回滚

### 13.1 实施阶段与依赖

| 阶段 | 范围与主要落点 | 完成门禁 |
| --- | --- | --- |
| S0 契约与可信身份 | Goal/Issue、Plan/action、全新鲜指纹、实际路径清单、能力 preflight | 来源不丢失；旧客户端不变；改文件内容立即使证据失效；接受过程可恢复 |
| S1 独立评测 | 受控 Eval Runner、候选快照、EvalSpec/Run、证据详情；先人工预备工作区 | 执行在声明候选；环境错误不记代码失败；命令/数据/版本绑定完整；仍保留用户确认 |
| S2 审查与有限修复 | 独立 Reviewer 门禁、逐条件 findings、修复策略与跨 Run 预算 | 自审不放行；两次上限和重复失败停靠；恢复不重复修复或发送 |
| S3 并行与集成 | 两个独立实现槽位、产物依赖、预备集成工作区、最终全树验证 | 分支通过但集成失败不能交付；用户已有改动保留；缺能力自动降并发或停靠 |
| S4 可选自动供给 | 经授权的会话/worktree 供给、生命周期与容量管理 | 创建结果未知可对账，取消不删除产物；可测收益后才扩大并发 |

顺序为 S0 → S1 → S2 → S3；S4 依赖前三阶段实测，不是首版前提。S0–S2 可先串行使用一个预备执行区验证闭环。S3 明确集成标准后，才评估对完全确定性契约开放自动目标判定。没有必要因 Swarm 一次重构所有 Team 模块。

### 13.2 关键验证矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 模糊目标、遗漏条件、实现降级成建议 | 保留原话与未知项，不能自动 satisfied |
| Agent 改阈值、删测试、伪造输出 | 规格完整性失败，伪造记录不能成为 Eval 事实 |
| 原地改写文件、编辑未跟踪文件、提交相同内容 | 前两者即时失效；相同内容提交可复用；不依赖 30 秒缓存 |
| 评测期间源输入变化、工具链/数据变化 | 冻结对象不被替换，受影响证据失效或重评 |
| 测试超时、缺依赖、flaky、非零退出 | 区分 inconclusive 与 failed；重复通过不能掩盖失败历史 |
| 自审、同 session 不同 member、串读其他裁决 | required 独立审查不放行，首次裁决上下文可核验 |
| 两分支分别通过但集成接口冲突 | 集成候选失败，无最终成功投影 |
| 共享 Run 多事项、一项修复或取消 | 按条件和产物归属影响；不取消其他事项共享任务 |
| 预算耗尽、同错误两次、amend | 有界停靠；新 Run 不重置累计消耗 |
| 接受/派发/运行完成/落账各窗口崩溃 | 可恢复同一意图；无重复发送、双记预算、旧 attempt 覆盖 |
| 暂停、取消、迟到结果、工作区被外部修改 | 停止新派发并保留真实副作用；不强行覆盖或清理 |
| 旧 Run/旧客户端、新事件、开关关闭 | 原流程可读，新状态保守展示，已接受工作不遗失 |

实现阶段先做契约判定、DAG 门禁和恢复的定向 Go 测试及竞态检查，再运行全仓 Go test/vet/build 与现有 Node 测试。前端阶段先完成依赖 preflight，再用真实浏览器验证桌面和 390px 手机：条件/证据/阻塞可见，队列三操作不退化，结果确认不执行文件操作。

端到端使用隔离数据、受控工作区和确认过身份的测试 Agent；先核对实际 cwd、适配器与测试标记，再注入故障，不能只凭会话创建成功判断测试替身已接管。补一次受控真实适配器验收，记录输入/Run/Task、候选、评测与事件身份；模拟 Agent 结果不能替代真实适配器能力验证。

### 13.3 兼容、灰度与回滚

Swarm 默认关闭，按 Team 和新 Run 显式启用，策略在创建时快照；旧执行不自动迁移或重跑。运行事实采用版本化 schema，先验证新增字段的 JSON 往返和 journal 重建；新操作要求客户端声明支持该契约版本。旧客户端只接收兼容的执行事实与保守结果摘要，服务端不能把未知检查映射为 passed，也不能假定旧页面会识别新增状态。

先在隔离 Team 记录基线，再观察需求遗漏、独立审查发现、修复次数、集成失败、环境失败、人工介入、端到端耗时与可观测成本。评估按相似任务和复杂度分组；不承诺未经测量的加速倍数。提高并发必须有吞吐改善且回归、预算、人工介入未恶化的证据。

回滚先关闭新 Swarm 准入，停止新自动修复，继续对账和收账在途任务；保留契约、候选、评测、确认和 journal。未结清意图及执行前不得回退到不识别新事件的旧网关，必要时保留兼容版本只读/恢复。关闭开关不取消队列、不删除 worktree、不撤销已有改动。

实际落地范围以实施记录为准，未实施能力不得由本设计推导为已经验证。网关加载改动仍由用户决定并执行重启，禁止自行运行 `make restart`。
