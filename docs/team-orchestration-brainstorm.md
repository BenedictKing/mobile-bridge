# 团队编排与事项视图头脑风暴

状态：设计建议，尚未实现；2026-11-11。

## 1. 用户对象与执行对象

- Issue 是用户要完成的事，也是画布、看板、侧栏进度的共同对象。
- 原话是需求证据，允许多对多关联；删除单个 Issue 不删除共享原话。
- Run 是一次执行记录，一个 Issue 可经历多次修订 Run，一个 Run 可服务多个 Issue。
- 看板默认展示 Issue；Run 留作事项详情中的执行历史，不能拿历史执行数量充当事项数量。
- 删除、取消执行、关闭追踪、撤销文件修改是不同动作，不互相隐含。

## 2. 按任务需要选择流程

| 类型 | 默认流程 |
| --- | --- |
| 简单咨询 | 澄清必要信息 → 查证 → 回答 |
| 调查分析 | 分头取证 → 交叉核验 → 综合结论 |
| 单点修改 | 检查现状 → 小计划 → 实现 → 定向验证 |
| 复杂实现 | 调研 → 核验 → 计划 → 并行实现 → 集成 → 验证与审查 → 修复复验 → 交付 |
| 外部操作 | 检查现状 → 可审阅操作方案 → 必要授权 → 执行 → 核实结果 |

不为凑人数拆任务。成员不足时顺序执行，阶段和证据要求保留。

## 3. 阶段产出与推进条件

- 调研：仓库现状、用户约束、参考资料、许可证、数据来源、接口与环境。
- 核验：来源是否权威和适用、版本是否一致、关键假设能否通过最小实验验证；明确未知项。
- 计划：保留原始目标，列出范围、接口、任务依赖、写入边界、验收方式与回滚策略。
- 实现：每个任务必须有明确输入、可观察输出、负责人、依赖和允许修改范围。
- 集成：接收各分支成果，检查接口一致、冲突、迁移和配置兼容性。
- 验证：用真实行为与失败路径证明需求覆盖，区别代码失败和环境未就绪。
- 审查：由未实现对应改动的成员评审；不能仅转述实现者的“测试通过”。
- 交付：列出已完成、未完成、测试证据、限制和需要用户操作的事项。

资料未核实就不得把关键假设当作实现前提。计划不是必须人工批准的表单。

## 4. 并行与写入协调

- 只并行依赖已经满足的任务；先约定接口，再拆前后端或独立模块。
- 同文件写入默认串行；可用独立工作区时仍需指定集成人和整体验证。
- 测试成员可先准备验收用例，但不能在实现前声称验收通过。
- 审查可以按完成模块提前开始，最终仍须检查集成后的版本。
- 缺失成员能力、账号不可用或预算不足时缩减并发，不能把任务默默交给不适合的角色。

## 5. 失败、修订与证据失效

- 调研无结论：记录证据缺口；只有影响关键决策时向用户提具体问题。
- 实现失败：只阻塞依赖该产物的分支，无关分支继续。
- 审查发现问题：建立指向原任务的修复项；不能重跑整个团队掩盖问题。
- 同类失败重复出现：限制重试次数和消耗，改变方法或停靠，不无限循环。
- 发送结果未知：按派发身份核对会话证据，不能按文本相似度认领，也不能自动重发。
- 网关重启：恢复已持久化计划、派发身份和阶段状态；不能重新生成一套冲突任务。
- 用户追加要求：区分补充信息、范围变更和独立事项；显式更新计划版本与受影响依赖。
- 代码、配置或数据发生变化：仅重做受影响验证；过期证据不能继续证明当前交付。
- 工作区被用户或其他 Agent 修改：检测冲突，保留外部修改，不强制覆盖或自动回滚。

## 6. 共享事项与共享 Run

- 不能把共享 Run 的全部任务进度直接当作每个 Issue 的完成进度。
- 建立 Issue → 目标条件 → 任务/证据的明确映射，无法归属时展示未知。
- 同一任务可服务多个 Issue，但取消某个 Issue 不得隐式取消其他事项需要的任务。
- 第一版若无法安全拆分共享执行，拒绝自动取消并解释原因，等待执行结束再删除。
- 删除后的 Issue 不应在事项看板再次出现；执行记录在独立历史入口保留。
- 对现有以 Run 为对象的看板，需要明确迁移策略，不能只前端隐藏同名行。

## 7. 用户介入与权限

- 系统负责生成计划、完成条件与检查配置；用户只处理目标取舍、必要凭据和真实授权。
- 用户确认与系统验证分离：用户满意不等于测试通过，测试通过也不自动代表满足需求。
- 不因流水线阶段变化重复请求已有授权；生产变更、发布及破坏性动作遵循实际权限。
- 显示具体阻塞对象和下一步；内部审查派发不能出现在用户消息的发送失败区域。

## 8. 第一版建议与验证

- 先统一 Issue 与 Run 的对象关系及看板口径，再增加阶段展示。
- 在现有调度 DAG 上增加阶段、产出与证据关联，沿用派发幂等和重启恢复机制。
- 负责人按任务复杂度选流程；服务端校验关键依赖，不能只依赖提示词让 Agent 自觉遵守。
- 计划和证据随版本持久化，图节点展示实际任务与阶段，而不是装饰性的固定步骤。
- 验证矩阵覆盖：咨询、单点修改、并行实现、共享任务、缺成员、环境失败、审查返修、重启、追加需求、取消和发送未知。
- 交付门禁覆盖：计划前不得派发依赖计划的实现；重复事件不重复派发；验证失效后不得展示通过；删除不影响共享原话或其他事项。

待实施前明确：历史 Run 如何归属存量 Issue；无 Issue 的执行记录入口；共享运行任务的取消策略；阶段证据的最小数据结构。

## 9. 当前实现与第一轮对照

代码复核发现以下偏差（2026-11-11）：

### 9.1 事项状态来源

- **进度与任务数**：取自最新关联 Run 的全部任务（`teamIssueProject:147–150`），包含规划、收口及服务其他事项的任务，违反 §6 不混入其他事项任务的原则。
- **确认与关闭**：存在 `Run.Goals[scopeId]`（`goal_review.go:209`），新 Run 关联后旧记录因范围哈希变化失效，用户追加条件丢失。
- **最新 Run 判定**：按 `RunsByTeam` 创建时间倒序取首项（`team_issues.go:311–317`），共享原话的修订可使无关 Run 成为事项的"最新"。

### 9.2 共享 Run 的耦合

- **审查与验证**：`goalCheckEvidence` 不区分范围（`goal_outcome.go:227–247`），共享 Run 中任一事项的失败审查阻止全部事项确认。
- **证据哈希**：覆盖整个 Run 任务列表（`goal_outcome.go:122–128`），任何任务变更使所有关联事项的确认失效。
- **审查过期**：任何写任务完成后标记同 Run 全部已绑定审查为过期（`runner.go:2596–2624`），不限于被审文件。
- **最终结果**：`FinalGoalResult` 无范围参数（`goal_outcome.go:136–182`），每个事项显示同一 Run 的合并输出。
- **取消与删除**：只到 Run 级，无任务级取消；删除事项时服务端拒绝活跃 Run（`team_issues.go:213`），共享 Run 保护仅在前端（`team-canvas.js:679`）且依赖可能过期的缓存列表。

### 9.3 工作区指纹

- **覆盖范围**：HEAD、diff、未跟踪文件名（`teams_workspace.go:324–343`），整个项目目录而非任务涉及路径。
- **确认后复核**：`GoalOutcome` 每次投影时重新校验（`goal_review.go:250–255`），工作区变化使已确认事项回到待验证（`TestGoalRequiredEvidenceTracksCurrentWorkspace:L275–312` 固定此行为）。
- **提交即失效**：提交已审查改动后 HEAD 和 diff 变化，确认立即阻塞；自动提交工作流下无法达成确认。
- **未跟踪盲点**：只记录文件名不含内容（`ls-files --others`），编辑新文件后指纹不变。

### 9.4 路由与归类

- **实时归类**：新原话的归类在 Lead 控制回合内完成（`runner.go:1632,2805` 注入 `IssueAssociationBriefing`），无单独派发开销。
- **共享 Run 默认**：活跃 Run 存在时新原话自动追加为后续任务（`inputroute.go:147–150`），不区分事项归属；路由先于归类。
- **修订重置归类**：`input_revised` 清空 `AssociationProposalID` 和链接（`inputqueue.go:1016–1021`），已分类原话修订后变回待归类。

### 9.5 看板与列表

- **对象不一致**：看板面板列 Run（`team.js:1041–1074` `renderRuns`），画布已展示事项（`team-canvas.js`）。
- **列表开销**：事项列表为每个事项克隆全部 Run 并重算目标（`team_issues.go:164,235–386`），每次轮询多次 git 调用。
- **归类 Run 过滤**：Run 列表排除归类专用 Run（`teams.go:736`），但派发额度计入全部 `task_dispatching` 事件（`inputroute.go:252–282`）。

### 9.6 限制与阈值

- **默认上限**（`model.go:326–339`）：12 任务/Run、3 轮次、2 活跃 Run、48 派发/24 小时、64 待路由原话。
- **轮次语义**：Lead 动作自行声明 `round`，只校验范围不强制递增（`actions.go:1312`）；真实约束是任务上限。
- **复杂流程**：八阶段实现需约 15 任务（根规划、研究、验证、计划、并行实现、集成、审查、修复、汇总），超出 12 任务上限，需拆分多个 Run。
- **额度消耗**：每个复杂事项约 15 次派发，每条新原话额外 1 次归类（实时）或 2 次（历史回填），日预算支撑约 3 个复杂事项。

### 9.7 阶段与证据

- **无阶段字段**：`graph.go` 的"阶段节点"是任务 ID 聚合投影（L64–229），Task 无 `phase` 字段。
- **类型隐含**：审查、收口、分流、归类专用、写锁通过布尔或枚举字段标记，无统一类型。
- **审查独立性**：提示词要求未参与实现的成员审查（`actions.go:967`），服务端未校验审查者与被审任务成员。
- **验证归因**：`ExitCode=-1` 区分环境问题（cwd 无法解析、超时）与代码失败（`verify.go:123–131`），但 `goalCheckEvidence` 统一标记为 `failed`。

### 9.8 无 Issue 的执行记录

历史回填跳过（`team_issues.go:47–59`）：显式计划 Run、定时 Run、broadcast/pipeline 模式、已删除或忽略的原话。当前看板仍为 Run 列表，迁移到事项视图后需独立入口。

## 10. 四个遗留问题的建议答案

### 10.1 历史 Run 如何归属存量 Issue

**当前路径**：`handleTeamIssueBackfill` 为 AutoPlan single 模式 Run 的目标与后续原话各创建历史输入，触发独立归类 Run（`team_issues.go:82–151`）。

**成本**：每条历史原话消耗 2 次派发（归类 + 实际路由），大批量回填耗尽日预算并阻塞新输入。

**建议方案**：
- 保持现有回填机制，明确标注历史事项（`input.Historical` 已存在），前端折叠为"历史记录"分组而非与当前事项平铺。
- 回填操作由用户触发并展示预估成本（原话数 × 2 对比剩余日预算），避免静默消耗额度。
- 归类 Run 计入派发额度符合设计（防拆分绕过成本控制），无需排除；额度不足时回填停靠并提示。

**无 Issue 的执行记录入口**：
- 定时 Run 按 `schedule` 分组展示为常驻事项，每次触发记录在该事项的执行历史下。
- 显式计划、broadcast/pipeline、未归类输入的 Run 归入"未分类执行"独立区域，按创建时间列出。
- 事项看板与执行记录视图分离：看板按状态分组事项并显示事项计数，执行记录按时间列全部 Run 并标注关联事项（可为空）。

### 10.2 共享运行任务的取消策略

**现状问题**：
- 取消只到 Run 级（`runner.go:3450–3530`），无任务级取消接口。
- 服务端拒绝删除有活跃 Run 的事项（`team_issues.go:213`），共享 Run 检测仅在前端（`team-canvas.js:679`）且可能用过期缓存。

**建议方案（第一版）**：
- **服务端保护**：删除事项前检查关联 Run 是否被其他事项引用，共享活跃 Run 时返回 `409 Conflict` 并说明共享关系，不自动取消。
- **关闭追踪与取消执行分离**：允许用户关闭事项追踪而不取消共享 Run，记录关闭原因；执行继续为其他事项服务。
- **任务级取消**（后续）：基于事项到任务归属（§10.3），提供按事项取消其专属任务的接口；共享任务仍拒绝单方取消。

**关键取舍**：
- 保守拒绝自动取消共享 Run，要求用户等待执行结束或手动介入，避免中断其他事项。
- 删除事项不回滚已产生的文件改动或外部操作，execution 记录保留在 Run 历史中。

### 10.3 事项到任务的归属推导

**目标**：每个事项的进度、最终结果、验证状态只计入服务该事项的任务，不混入共享 Run 的其他事项任务。

**数据基础**：
- `IssueInputLink.SourceStart/End` 与 `WorkItem.SourceStart/End` 都是同一 `input.Revision` 正文的 rune 区间（`issueproposal.go:46,135–142`；`inputqueue.go:118,125–129`）。
- 区间重叠 → Issue 关联该 WorkItem → 该 WorkItem 的 `TaskIDs` 属于该 Issue。

**归属规则**（无需新账本）：
1. **精确匹配**：Issue 链接区间与 WorkItem 源区间重叠 → 该 WorkItem 的任务归属该 Issue。
2. **机械路由回退**：WorkItem 无源区间（`MarkRouted` 默认创建，`inputqueue.go:748–762`）→ 指向 Lead 控制任务，派生任务按任务 ID 前缀回溯（`ActionDerivedTaskID`：`{source}-{d|s}{round}-{index}`）。
3. **无法归属**：Lead 规划、Reduction 汇总、无血缘任务标记为共享，按 Run 级展示。

**实施**：
- 投影时按上述规则过滤任务列表，计算事项专属进度（`completed/total`）。
- 最终结果优先取归属该事项的 Reduction 或最后完成任务，回退到 Run 级结果并标注"包含共享任务输出"。
- 审查与验证证据同样按归属过滤：某事项的失败审查不阻止无关事项确认，除非证据属共享任务。

**限制**：
- 首版不支持 Lead 在动作中显式声明任务服务哪些事项；归属完全由原话区间推导。
- 共享工作区写锁使"并行实现"实为串行，隔离 worktree 下才有真并行但需集成阶段。

### 10.4 阶段证据的最小数据结构

**复用现有类型**：扩展 `GoalEvidenceRef`（`goal_outcome.go:35–43`），增加字段而非新建结构。

**必需字段**：
- `Kind`：已有 `user_assessment | task_result`，新增 `research | plan | verify_command | review_verdict | integration`。
- `Subject`：指向的条件 ID 或任务 ID，区分不同条件的证据。
- `WorkspaceHead/WorkspaceDiff`：证据采集时的工作区版本（复用审查绑定字段 `HeadRevision/DiffHash`）。
- `Validity`：投影时计算，比较证据版本与当前版本，标记 `fresh | stale | unknown`。

**存储位置**：
- 每个 `GoalCriterion.EvidenceRefs` 列出支持该条件的证据（`goal_outcome.go:32`），而非所有条件共享同一批引用。
- 证据随 `goal_reviewed` 事件持久化（`goal_review.go:209–210`），journal 重放可恢复。

**阶段标签**（可选）：
- Task 增加可选 `Phase string` 字段，Lead 在 `delegate` 动作中声明，网关校验不为空且不超长。
- 服务端门禁：实现任务的依赖中必须有已完成的计划任务（可配置豁免）；审查任务依赖中必须覆盖全部被审任务。
- 阶段本身不是状态机，只是任务分类标签；顺序由 DAG 依赖表达，现有调度器无需改动。

**不引入的复杂度**：
- 不建固定八步流程渲染，阶段名称和数量由 Lead 按需声明。
- 不建 Run 级阶段状态，避免与 Task 状态双重同步；阶段进度从任务状态折叠得出。
- 不自动推断阶段类型，显式声明或从现有字段派生（`Review=true` → review，`WriteLock=exclusive` → implement）。

## 11. 边界情况与反例

### 11.1 事项生命周期

- **删除后重现**：Issue ID 由 `teamID + inputID + revision + title` 确定性生成（`issueproposal.go:109–113`），无墓碑；共享原话删除某事项后，该原话保持已分类状态（`AssociationProposalID` 不清空），不会重新提议。
- **修订后孤立链接**：原话修订清空归类状态（`inputqueue.go:1016–1021`），事项的 `IssueInputLink` 指向旧 `revision`，投影时因版本不匹配跳过（`team_issues.go:253–254`），事项变为空范围。
- **后续原话改变最新 Run**：共享原话的两个事项 A 和 B，B 的后续原话创建新 Run，A 的"最新 Run"变为 B 的 Run（按创建时间倒序），A 的状态受 B 的 Run 驱动。
- **确认后范围扩大**：事项 A 已确认，后续原话关联到 A 使范围哈希变化，旧 `GoalRecord` 因 `scope.Hash` 不匹配失效（`goal_outcome.go:283–286`），A 回到待评估。

### 11.2 共享与隔离

- **共享 Run 是默认**：活跃 Run 存在时后续原话自动追加（`inputroute.go:147–150`），Lead 无法主动请求拆分到新 Run。
- **工作区指纹过粗**：项目目录任何改动（其他 Run 提交、手动编辑、新分支切换）使所有必需检查的事项回到待验证。
- **未跟踪文件盲点**：只记录文件名（`ls-files --others --exclude-standard`），编辑已列出的未跟踪文件不改变指纹，审查后的内容变更未被捕获。
- **提交使审查失效**：Agent 自动提交已审查改动后 HEAD 和 diff 变化，`checkGoalWorkspaceEvidence` 阻止确认（`goal_review.go:236–244`），需重新审查同一内容。

### 11.3 归类与路由

- **归类后修订**：修订已归类的排队原话后归类状态清空，旧提案和链接丢失，再次路由时按新正文重新归类（可能生成不同 Issue ID）。
- **澄清事项无 Run**：原话被标记为 `clarification` 后不创建执行 Run（`IssueSegmentClarify`），事项无关联 Run，无法关闭（关闭需终态 Run）。
- **忽略片段无归属**：一条原话部分片段 `ignore`，该部分文本不属于任何事项；删除关联事项后该片段仍无归属，原话的完整覆盖不变量被打破。

### 11.4 审查与验证

- **单成员团队无独立审查**：只有 Lead 时无合格审查者（`IsReviewTask` 排除 Lead），必需审查变为 `not_required` 或标记"无独立审查者"。
- **同成员自审**：审查任务成员与被审任务成员相同时服务端不拒绝，只有提示词要求独立性（`actions.go:967`）。
- **验证环境失败与代码失败**：`ExitCode=0` 通过，`!=0` 失败，`-1` 是环境问题（`verify.go:207,214,218`），但 `goalCheckEvidence` 统一标记 `failed`（`goal_outcome.go:237`），无 `unknown` 分支。
- **审查后再次写入**：共享 Run 中后续任务写入文件，已完成审查被标记 `ReviewVerdictStale`（`runner.go:2612`），即使写入未触及被审文件。

### 11.5 派发与预算

- **历史回填耗尽预算**：每条历史原话 2 次派发（归类 + 路由），48 预算支撑 24 条，大批量回填阻塞当日新输入。
- **复杂事项额度占用**：15 任务的实现流程消耗约 1/3 日预算，3 个此类事项加常规对话可能耗尽。
- **轮次非强制递增**：`round` 只校验范围（`actions.go:1312`），Lead 可复用 `round=1`，真实约束是 12 任务上限而非 3 轮次。

### 11.6 删除与取消

- **删除共享原话的事项**：原话保留并继续关联其他事项（`issueproposal.go:360–385`），被删事项的片段不再属于任何事项但原话仍标记已归类。
- **删除检查竞态**：前端读取事项列表判断共享（`team-canvas.js:679`），服务端只拒绝活跃 Run（`team_issues.go:213`），列表过期时可能漏判。
- **取消不回滚**：Run 取消不删除已写入文件或已执行外部操作（`runner.go:3460–3530`），产物和副作用保留。

## 12. 分阶段实施建议

按复杂度与依赖排序，优先低成本高价值修复：

### 阶段 0：保护性修复（1–2 天）

**目标**：关闭已知数据正确性与保护缺口，无模型变更。

1. **共享 Run 删除保护移到服务端**：`handleTeamIssueDelete` 检查关联 Run 是否被其他 Issue 引用，共享时拒绝并返回共享 Issue 列表。
2. **审查独立性校验**：解析 `reviewOf` 后比较审查任务成员与被审任务成员，相同时记录 `reviewIndependence: false`，前端标注"非独立审查"。
3. **验证环境失败区分**：`goalCheckEvidence` 对 `ExitCode=-1` 标记 `unknown` 而非 `failed`，reason 注明 cwd 或超时。
4. **修订后归类保护**：排队原话的修订保留 `AssociationProposalID` 和已有链接，避免重新归类产生重复 Issue。

**验收**：共享 Run 删除返回 409；自审标注非独立；环境失败显示 unknown；修订不重置已归类状态。

### 阶段 1：事项状态独立（3–5 天）

**目标**：事项的确认、关闭、用户追加条件不依赖单个 Run。

1. **目标契约移至 Issue**：InputLedger 增加 `IssueGoals map[issueID]*GoalRecord`，`goal_reviewed` 事件同时写 Run 和 Issue（兼容期双写）。
2. **投影优先读 Issue**：`issueGoalScope` 构造范围哈希，优先从 `IssueGoals[issueID]` 读取契约；Run 级记录作为执行证据引用。
3. **关闭独立于 Run**：允许用户关闭事项追踪而不取消 Run，`issue_closed` 事件记录原因，投影不再要求终态 Run。
4. **确认后稳定**：确认记录绑定工作区指纹，后续投影不再重新校验；展示"已于版本 X 确认，当前版本 Y 已变化"而非回退到待验证。

**验收**：新 Run 关联后已确认事项保持 satisfied；用户可关闭有活跃 Run 的事项；确认不因无关提交失效。

### 阶段 2：任务归属与进度隔离（4–6 天）

**目标**：每个事项的进度只计入其专属任务。

1. **归属推导函数**：`IssueTaskAttribution(issue, run)` 按 §10.3 规则返回任务 ID 列表。
2. **事项进度重算**：`teamIssueProject` 按归属任务计算 `completed/total`，标注共享任务数。
3. **最终结果过滤**：`FinalGoalResult` 增加 `issueID` 参数，优先取归属该事项的 Reduction 或最后任务，标注是否含共享输出。
4. **审查证据作用域**：`goalCheckEvidence` 按归属过滤审查任务，A 事项的失败审查不阻止 B 事项确认（共享任务除外）。

**验收**：共享 Run 的两事项显示不同进度；某事项完成不使另一事项自动完成；失败审查只阻止相关事项。

### 阶段 3：工作区证据细化（5–7 天）

**目标**：证据绑定到实际内容而非 commit，减少误判。

1. **内容指纹**：`Fingerprint` 返回 git tree hash（临时 index 写入全部跟踪+未跟踪文件）代替 HEAD+diff，相同内容提交前后指纹一致。
2. **路径作用域绑定**：TaskResult 增加 `TouchedPaths []string`（从 `FileSummary` 解析），审查绑定到被审任务的路径集合。
3. **过期判定细化**：只有 `TouchedPaths` 内文件的 tree hash 变化时标记审查过期；verify 保持全树校验。
4. **Git 调用缓存**：按 cwd 和 mtime 缓存指纹结果 30 秒，减少列表轮询开销。

**验收**：提交已审查内容不使审查失效；编辑无关文件不触发重新审查；列表响应时间不随事项数线性增长。

### 阶段 4：阶段标签与门禁（3–5 天）

**目标**：可选的阶段声明与最小服务端检查。

1. **Task.Phase 字段**：可选 string，Lead 在 delegate 动作中声明，网关截断到 64 字符。
2. **门禁规则**：写锁任务的依赖中必须有已完成计划任务（Team.Policy 可配置豁免）；审查依赖必须覆盖全部 `reviewOf` 任务。
3. **违规修复循环**：门禁失败生成 repair prompt 返回 Lead，同 action 解析失败的修复机制。
4. **前端阶段展示**：事项卡按 Phase 分组任务并折叠，标注各阶段状态；无 Phase 的任务归入"其他"。

**验收**：实现任务缺少计划依赖时 Lead 收到修复提示；前端按阶段折叠任务；阶段为空的旧 Run 仍正常显示。

### 阶段 5：看板迁移到事项视图（2–3 天）

**目标**：看板对象从 Run 改为 Issue，Run 列表移至独立入口。

1. **看板接口切换**：`TeamsPanel` 请求 `/api/teams/:id/issues` 代替 `/runs`，按 `issue.status` 分组（open/in_progress/waiting/resolved/closed）。
2. **无 Issue 执行入口**：新增"执行记录"标签页列全部 Run，标注关联 Issue（可为空），显式计划、定时、归类 Run 各有图标。
3. **历史分组**：`issue.historical` 的事项折叠到"历史记录"分组，默认收起。
4. **Run 详情保留**：点击事项卡打开事项详情，其中列出关联 Run；Run 详情页入口保留供直接访问。

**验收**：看板显示事项而非 Run；每个非终态 Run 可通过事项或执行记录访问；历史事项不与当前平铺。

### 阶段 6：定时与显式计划支持（按需）

**目标**：定时 Run 与显式计划 Run 有稳定入口。

1. **定时事项**：每个 `TeamSchedule` 生成伪 Issue，标题为 schedule 描述，关联该 schedule 触发的全部 Run。
2. **显式计划入口**：`/api/teams/:id/runs?filter=explicit-plan` 返回显式计划 Run 列表，前端"计划执行"标签页展示。

## 13. 待用户决策的开放项

以下五项影响产品行为，建议在阶段 0 前明确：

### 13.1 确认后工作区变化的处理

**选项 A**（当前行为）：每次投影重新校验工作区，变化后回到待验证。
**选项 B**（建议）：确认绑定到确认时指纹，后续只展示"已于版本 X 确认，当前 Y"，不回退状态。

**权衡**：A 保证展示结果与当前代码一致但使已确认事项频繁退化；B 稳定已交付状态但需用户主动关注"当前版本已变化"提示。

**建议 B**：确认是时间点事实，后续变化通过新信号（如回归检测）而非撤销确认来处理。

### 13.2 共享 Run 的避免策略

**选项 A**：保持当前路由（活跃 Run 时追加），通过任务归属隔离影响。
**选项 B**：归类先于路由，归类结果显示事项归属不同时创建新 Run。

**权衡**：A 无额外派发成本但需完整实施归属与证据过滤；B 避免共享但每条新原话多 1 次派发且增加延迟。

**建议 A**（第一版）：任务归属与证据过滤的实施成本低于重构路由顺序，且保持实时归类的零额外派发。

### 13.3 复杂流程的容纳方式

**选项 A**：提升单 Run 任务上限（如 12 → 24），复杂流程在一个 Run 内完成。
**选项 B**：保持 12 任务限制，复杂流程拆分到多个 Run，通过 amend 链接并缓存中间结果。

**权衡**：A 简化编排但单次失败成本高、并发槽位占用久；B 符合成本分段控制但 Issue 状态需跨 Run 维护（阶段 1 已解决）。

**建议 B**：限制是有意的成本控制，Issue 级状态已支持跨 Run，分段执行提供更细的检查点。

### 13.4 实现类交付的独立审查要求

**选项 A**：实现类交付（`deliverableKind=change`）在有合格审查者时强制要求独立审查，缺失时阻止确认。
**选项 B**：审查作为可选最佳实践，Lead 可声明 `review=false` 并记录原因。

**权衡**：A 提升质量门槛但单成员团队或紧急修复受阻；B 灵活但依赖 Lead 自觉。

**建议 A + 豁免机制**：默认要求独立审查，Lead 可通过显式动作 `review=false, reason="紧急修复"` 豁免并记录到交付证据。

### 13.5 交付类型的设定与变更

**选项 A**：Lead 在首次规划时声明 `deliverableKind`，后续变更需用户确认。
**选项 B**：`deliverableKind` 始终由用户在目标表单设定，Lead 无权更改。

**权衡**：A 减少用户操作但 Lead 可能误判；B 确保用户掌控但增加交互。

**建议 B**：交付类型决定验收标准，应由用户明确，默认 `result`；Lead 建议但不直接变更。
