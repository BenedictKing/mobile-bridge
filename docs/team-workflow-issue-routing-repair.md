# Team Issue 归类与 workflow 修复

日期：2026-11-20。

## 根因

长消息的 Issue 归类协议要求模型自行填写精确 Unicode rune 区间。模型连续只修正第一个遗漏字符，整批委派动作因此未通过校验。
主控和纠错简报要求只输出动作块，同时附加简报又要求 Issue 块，形成矛盾。原拆分示例还包含重叠区间，不能作为有效提案参考。
纠错耗尽后仍把最后一次回复记为任务完成，任务状态折叠随之生成 `run_completed`，丢失业务编排失败语义。

## 修复

整条消息属于同一主题时，模型只选择语义分类与 `source=full`，网关解析全文为 `[0,runeCount)`：

```json
{"inputId":"当前输入 ID","revision":1,"segments":[{"action":"create","newIssueTitle":"按计划实现","source":"full"}]}
```

`full` 必须用于唯一片段，不能混合显式数字区间。持久化前解析为精确数字区间，原文和来源不变；既有数字区间提案与历史账本继续受支持。
多主题提案仍严格校验覆盖、重叠和版本，不擅自扩大模型的归类范围。遗漏错误提供完整连续遗漏区间、全文长度和有界原文片段。
主控与纠错统一允许本回合所需的 Issue 块和动作块，历史归类继续只允许 Issue 块；去掉重叠拆分示例。
最终协议校验失败或无法继续创建纠错任务时，最后一个任务落 `failed`，Run 随任务失败收场。保留原始回复、原生 turn 的结束原因和编排失败原因，Journal 重建后仍可核对。

## 回归范围

- Unicode/emoji 全文来源解析、持久化与重放。
- 非法来源、全文与部分区间混用、重叠/遗漏的严格拒绝。
- 既有数字区间兼容与完整遗漏诊断。
- 连续四次校验失败：无委派执行、无 `run_completed`，失败原因与原始回复可重建。
- 一次纠错后完整执行：计划核对 → 成员实现 → Lead 核验 → 控制会话最终交付。
- 实现等待计划结果，核验等待实现结果，纠错后不重复派发。

workflow 用例使用真实 Team 调度、动作解析、队列与 Journal 代码，以及 Go fake Agent 会话；不代表真实模型或 movie-maker 实现已经验收。

## 验证与加载

以下门禁全部通过：`go build ./...`、`go vet ./...`、`go test ./...`、`go test -race -count=1 ./...`，普通与竞态检查均为 40 个有测试的包零失败；本次 Go 文件的 gofmt 检查与差异空白检查通过。
HTTP 集成回归同步更新了先前“格式失败仍应 completed”的旧断言，确认纠错耗尽与修复 ID 超限均以失败终局收场，并检查原始结果和 Journal 事件。
本补丁不自动重写历史已结束 Run；要让运行中的网关加载修复，按项目约定由用户执行重启，再修订或重新发送该需求。
