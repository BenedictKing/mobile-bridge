# 目标驱动的并行 workflow 规划

日期：2026-11-21。
状态：已实现，验证记录见第 6 节。

## 1. 范围与兼容

新版团队聊天与普通聊天的团队派发使用 `teamIssueRoutingVersion="2"`。
输入账本保存 `planningVersion=1`，新创建的自动规划 Run 保存独立的 `planning` 状态。
旧客户端、显式计划、历史归类、专用 Swarm 模式与既有 Run 保持原协议；不改写已结束的真实运行记录。

目标结果页和事项详情移除反馈、完成条件与逐项核对表单，仅展示结果及检查证据。
用户从团队聊天发送补充需求，主控先关联 Issue，再引用已有 workflow 派发补充工作。
同一 Run 可以追加更严格的验收条件和新的独立 workflow，不能删除或缩小已有要求。

## 2. 规划与评估协议

复用 `team-actions` 信封，顶层增加 `plan` 和仅评估任务可提交的 `feedback`。
首次实质派发必须提供完整目标的 `criteria` 与独立交付的 `workflows`；delegate 必须引用 `workflowId`。
每个 workflow 自己完成实现与检查，公共契约可以前置，独立分支不串成无必要的依赖链。
真实依赖继续使用 `key/dependsOn`；审查用 `reviewOf` 绑定被审任务，不等待无关分支。

评估逐项返回 `met/unmet/unknown`、证据任务 ID、缺口及阻塞：

- `complete`：全部条件有已完成执行任务的可读证据，必要检查有效通过，无剩余动作或缺口。
- `continue`：明确剩余工作，同时派发至少一个实际任务，仅补缺口并复用已有成果。
- `blocked`：已无法推进，明确权限、环境或外部资源阻塞，保留成果等待用户处理。

空结果、主控规划和评估任务不能作为完成证据。普通进度文字须由评估核对产物，不能仅凭回合结束验收。
协议错误沿用有界纠错；评估纠错仍保留完整目标、冻结条件、执行事实与反馈协议。

## 3. 并行执行与隔离

执行线程和会话按 `Run + member + workflow` 幂等创建。
同一成员的不同 workflow 可以并行，同一 workflow 的同一成员会话仍互斥。
团队并发上限、供应商 AIMD 限流、预算和活动 Run 上限继续生效；瞬时繁忙的 workflow 保留为计划任务排队。

目录写锁按 Run 与任务共同确定归属：同目录写任务串行，只读任务可与写任务并行；不同 Run 的同名任务不能共用持锁身份。
独立写任务可以引用用户已登记的不同 `workspaceId`，分别持锁执行。
不会自动创建 worktree、分支、合并或清理工作区，也不会绕过共享目录写锁。
任务详情和阶段图显示 workflow 归属，目标评估有单独标题。

## 4. 续跑与停止

每批任务结束后，网关自动创建只读的 `lead-goal-check-N`，替代仅汇总一次的收尾。
评估任务接收完整本轮目标、前轮血缘、冻结规划、任务状态、空结果事实与检查记录。
验证失败也回送目标评估，修复派发后清除旧检查，重新执行验证。

目前每 Run 最多 3 次目标评估；连续两次没有新增证据或验收进展也停止自动续做。
改写缺口文字不算进展。原有任务数量、预算、超时、供应商限流及用户暂停/取消继续生效。
目标未完成但资源上限已到、自动派发关闭或真实阻塞时进入 `waiting_input`，不标记 completed。
未耗尽上限时，显式“继续”会重新派发评估；已耗尽时需聊天启动后续修订，不自动增加预算。

## 5. 事件与恢复

`goal_planning` 记录冻结规划、评估轮次、逐项结果与续做决定，和任务结算及动作提案同批落账。
workflow 派发任务保留 ID、执行线程、工作区、写锁、提示词及依赖，事件可重建快照。
失败改派保留 workflow，按接手成员重新确定独立线程；审查格式修复和指定任务追问继承原分支。
评估任务与协议修复重建后仍是只读；恢复不会把 waiting_input、暂停或取消折叠为成功。

机器反馈即使没有正文，也能投影为可读的条件、证据任务、缺口与阻塞报告。
AI 验收通过和用户历史确认保留各自来源；未配置独立审查不伪造通过事实。
规划及评估说明总量各限制为 6000 字，并为派发消息中的固定协议预留上下文容量。
