## 1. 背景与目标

当前「团队」入口是一个窄弹窗，团队卡片按纵向重复排列。用户需要逐个展开 Run 才能知道：

- 有多少团队和成员；
- 哪些 Run 正在运行；
- 哪些 Run 等待处理或已经失败；
- 最近一次运行推进到了哪里；
- 进入详情后如何从阶段、任务、结果和错误继续排查。

本次目标是把入口改成一个团队运行工作台：先给全局状态，再给最近活动，再下钻到团队和 Run 详情。保留现有团队创建、聊天、Run、预算、定时、重命名和删除能力，前端复用已有接口，不改变后端编排语义。

完成后的首屏应该让用户在 3 秒内回答「现在有没有运行中的任务、哪里需要我处理、最近发生了什么」。

## 闭环契约：凡事有交代，件件有着落，事事有回音

这句话不是宣传文案，而是团队聊天和 Dashboard 的共同交互约束。每一条用户请求都必须带着同一条可追踪链路走完：

```text
用户请求
  ↓ 有交代：受理回执
负责人 / Run ID / 目标范围 / 首个检查点
  ↓ 有着落：执行状态
当前负责人 / 当前阶段 / 下一步 / 等待原因
  ↓ 有回音：进度与终局回执
最近进展 / 结果证据 / 验证状态 / 未完成项 / 后续动作
```

三条硬规则：

- **有交代**：发送成功后马上显示受理回执，至少包含 Run 标识、负责人、目标摘要和下一次回音的触发条件。只有受理成功才显示“已创建 Run”，排队、发送未知和失败分别显示各自状态。
- **有着落**：每个任务必须处于可解释状态：运行中、等待输入、等待依赖、已完成、已失败、已取消或结果未知。运行中必须显示当前阶段和负责人；等待状态必须说明等待谁或等待什么，并给出可执行动作。
- **有回音**：重要状态变化都要留下时间线事件；阶段完成、成员失败、需要输入、验证结束、Run 终止都要在聊天和 Dashboard 产生可见回音。终局必须给结果、证据、验证、未完成项和下一步，不能只显示“完成”。

“结果未知”是终局状态，不得静默重发或伪装成成功；它必须显示核查入口和人工对账动作。

排队发送有独立回执：`POST /api/teams/:teamId/inputs` 返回 `inputId` 和 `routeStatus` 时，只显示“已排队”、队列状态和下一次路由条件，不提前编造 Run ID。输入进入路由并关联 `targetRunId` 后，再把同一输入的回音链接到 Run。

## 2. 参考结论

参考 `refs/multica/` 的 Dashboard、运行 transcript 和实时刷新实现，吸收以下做法：

- 页面先按范围组织信息，再用 KPI、趋势/活动和明细分层；
- 页面级筛选放在顶部，卡片级视图切换放在卡片内部；
- 运行状态、错误诊断、消息 transcript 分开建模；
- 任务消息按序合并，工具调用和结果按不透明 `call_id` 配对；
- 合并后再做 secret redaction，避免凭据跨分片被漏检；
- `task:completed`、`task:failed`、`task:cancelled` 和 reconnect 都触发刷新；
- 新增未知 failure reason 时保留原始值，客户端不把诊断信息静默丢弃；
- 空状态只在没有诊断信息时显示，失败任务优先显示结构化原因和错误。

这些原则与当前 Run 详情已有的阶段图、统计卡、任务卡和事件补读机制一致，Dashboard 只补入口层的信息组织。

## 3. 信息架构

团队入口改为可深链工作台（`#teams`），与聊天共用同一应用框架和侧栏。侧栏顶部用一致的「聊天 / 团队」切换；聊天模式显示会话列表，团队模式显示团队列表；主内容区切换聊天、团队 Dashboard 或 Run。结构按下面顺序排列：

1. **页面头部**：团队运行标题、最近同步时间、刷新按钮、新建团队按钮。
2. **状态 KPI**：团队数、成员数、运行中 Run、需处理 Run。
3. **运行筛选**：全部、运行中、需处理；显示各筛选项数量，使用 `aria-pressed` 表达选中状态。
4. **最近活动**：按需处理、运行中、最近结束分组，组内按 `updatedAt` 倒序显示全部 Run 摘要；每行显示状态、团队、目标、任务进度、负责人、最近回音和下一步，点击进入 Run 详情。
5. **团队网格**：桌面端两列，窄屏单列；团队对话和新建 Run 保持为高频操作，预算、定时、重命名、删除收进团队管理区。
6. **空状态**：没有团队、当前筛选无结果、Run 摘要读取失败分别给出原因和下一步操作。
7. **闭环回音**：最近活动行和团队卡片补充负责人、最近回音、下一步和终局证据入口；没有新事件时显示“等待成员完成当前阶段”，不显示无意义的空白。

Run 详情保持现有页面作为第二层工作区，沿用同一应用侧栏并将「团队」标为当前工作区。信息顺序调整为：状态头部、停滞/等待提示、交付证据、统计、待决问题、动作预览、阶段图、任务列表。任务结果需要继续支持打开原会话、查看改动、工作区清理和诊断展开。

团队聊天按同一闭环呈现对话回音：

- **受理回执**紧跟用户请求，显示已受理/排队/失败之一、Run ID、负责人和目标摘要；
- **执行回音**贴近 Workflow，显示最近有意义进展、当前执行者和下一步；没有新事件时保留“等待谁/什么”的说明；
- **停靠回音**作为可操作消息显示原因、已有着落和恢复按钮；恢复失败仍保留错误及可重试入口；
- **交付回执**由 Lead 汇总结果、Agent 完成度、评审、验证、未完成项和证据链接；结果未知必须要求人工核查。

聊天和 Dashboard 消费同一个 Run summary / delivery projection，避免两处给出不同负责人、进度或结论。聊天负责把回音放在对话上下文里；Dashboard 负责聚合多团队的回音并分流。

### 团队聊天画布

团队聊天固定显示画布，不再提供「画布 / 对话」切换及「整理旧对话」入口。画布只呈现团队输入和独立 Issue，不把每条时间线 user row、Lead 动作信封或 Run 自动转换成 Issue。定期拉取仅在数据实际变化时重绘；对象字段顺序变化不算内容变化，缩放、平移、拖拽位置及关联高亮保持稳定。

自动排列按输入与 Issue 的关联关系分组，共享同一事项的输入放在同组；组按最早输入排序，组内保留原始输入顺序和序号。两侧共同预留高度，短气泡与较高事项组居中对齐。宽屏按可用宽度让独立小组并排，多事项组横向展开为多列，连线经行间通道进入卡片；手机端按「本组输入 → 本组事项」单列排列。初次打开按可读宽度呈现，完整总览仍由「显示全部内容」提供。

未关联事项的气泡提供「删除消息」按钮，确认后移除画布输入，保留 Run 执行记录。仍在路由或有未结束 Run 的消息不可删除；后端按输入版本检查冲突。删除事实持久化，刷新、重启和历史重新导入不会恢复已删除气泡。

事项详情可逐条打开关联 Run；手机详情将键盘焦点限制在面板内，Escape 关闭并恢复触发项焦点。Run 的「打开原会话」进入实际执行对话并定位结果引用的回合，顶部提供「返回 Run」；来源随浏览器历史保存，刷新后仍可返回。没有可定位的回合时明确提示，不用其他任务的回合替代。Run 返回按来源回团队画布或工作台，失效 Run 深链也保留返回入口。

点击 Issue 与点击关联消息均高亮事项、关联消息和连线，并将关联节点定位到可视区域；桌面避开右侧详情面板。详情中的「关联原话」按画布原始序号显示，每条可点击返回具体消息；手机点击后关闭全屏详情，保留关联高亮。

一次发送后的链路：

```text
发送消息
  → TeamInput 先落账，画布出现「正在关联」气泡
  → 主控 Lead 查看已有 Issue，返回带原文区间的结构化关联提案
  → 网关校验输入版本、来源区间完整覆盖、Issue 归属和幂等键
  → 原子记录 Issue 新建/关联事实
  → 同一气泡从待关联状态变为连到一个或多个 Issue
  → Issue 汇总所关联输入的 Run/WorkItem 执行状态、最近回音和证据
```

Lead 提案可以将一个消息的不同原文区间分别关联到已有 Issue、创建新 Issue，或说明一段内容需要澄清。每段非空白原文必须且只能覆盖一次；未知 Issue ID、重叠/漏项、过期 revision 和不属于当前 Team 的目标一律拒绝，不应用部分关联。关联事实与 TeamInput 一起追加到账本 journal，重复结算按 proposal ID 幂等；解析或校验失败时进入 Lead 修复回合，达到修复上限后将归类标为失败并保留原因，不伪装成已完成关联。

只有携带 `teamIssueRoutingVersion: "1"` 的新输入进入 Lead 归类；旧 journal、旧快照和旧客户端输入保持 `unclassified`，不显示为正在处理，也不根据历史 Run 标题或聊天文本猜测 Issue 关系。画布的“正在关联”状态只覆盖确实交给 Lead 处理的输入。

Issue 是独立持久化实体，含稳定 ID、标题和输入来源区间；InputIssueLink 保留原始输入 ID/revision、原文起止位置及提案批次。Issue 不复制 Task 状态：当前负责人、进度、最近回音、等待原因和交付证据从关联 TeamInput 的 Run/WorkItem 投影派生。一个 Issue 可汇总多条气泡和多个 Run；一个气泡也可连到多个 Issue。点击 Issue 展示关联原话、关联 Run/WorkItem 状态和证据，再可进入既有 Run 详情。

旧 Run 和旧会话只读保留，不从标题/目标文本自动猜测成新 Issue。切换后画布初始内容来自新账本 Issue；历史 Run 仍可从 Dashboard/Run 历史进入。网关生成的 `[Team delegation]`、`[Team context]`、`[Team review]` 信封不作为用户气泡。

本流程依赖 Lead 语义路由提案、WorkItem 来源引用及独立 Issue 账本。当前机械输入路由只负责把 TeamInput 送入 Lead Run，不具备 Issue 语义；不得把机械 follow-up/new-task 判定当成 Issue 归类结果。

## 4. 状态与数据模型

Dashboard 继续消费轻量 Run summary，不在团队列表中读取任务正文。为了让承诺可信，Run summary 需要新增由服务端从 Run 快照和事件账本派生的闭环投影；不让前端猜测或为每行再拉完整 transcript。首次打开和手动刷新并行请求：

- `GET /api/teams`：团队、成员、成员可用性和策略；
- `GET /api/teams/:teamId/runs`：目标、状态、更新时间和 `taskCounts`；
- 进入 Run 后继续使用现有 detail、`/stats`、`/graph` 和 changes 订阅。

Run summary 增补字段：

| 字段 | 来源 | 语义 |
| --- | --- | --- |
| `currentOwner` | 首个可推进的 `running` / `dispatching` 任务与成员投影 | 当前实际负责的成员；没有活动任务时为空 |
| `lastUpdate` | 最新的有意义 Run 事件 | `{kind, at, summary, taskId?}`；不展示原始日志或敏感内容 |
| `nextAction` | Run / task 状态与依赖图派生 | `{kind, label, actor?, reason?}`；告诉用户系统正在等什么或谁 |
| `delivery` | 现有交付证据投影 | completed/total、review、verify、pendingQuestions、结果摘要引用 |

`lastUpdate` 从 `task_planned`、`task_dispatching`、`task_running`、`task_completed`、`task_failed`、`task_stopped`、`task_cache_hit`、`run_stalled`、`run_verify` 等事件派生。对相邻、低价值的派发变化做归并；阶段完成、等待输入、失败、停滞和终局必须保留。字段只包含可展示摘要，不能携带 prompt 全文、工具 transcript 或凭据。

`nextAction` 不是模型自由生成的承诺时间。它由确定性规则产生：活动任务显示负责人和阶段；等待输入显示“等待你回答”；依赖未满足显示“等待前序任务”；验证中显示“验证中”；终态显示交付/修订/核查入口。结果未知显示“需要人工核查”，绝不显示“稍后自动完成”。

客户端状态集合固定如下：

| 分组 | 状态 | 用途 |
| --- | --- | --- |
| 运行中 | `created`、`dispatching`、`collecting`、`reducing` | KPI、运行中筛选、活动排序 |
| 需处理 | `waiting_input`、`paused`、`failed`、`outcome_unknown`、未知状态 | 顶部提醒、需处理筛选、醒目错误色 |
| 终态 | `completed`、`failed`、`cancelled`、`stopped`、`outcome_unknown` | 进度归档和最近活动 |

任务进度统一由 `taskCounts` 派生：

```text
total = sum(taskCounts.*)
completed = taskCounts.completed
progress = total > 0 ? completed / total : 0
```

缺少 `taskCounts` 时显示「进度待同步」，不猜测为 0。未知 Run 状态保留原始字符串并显示通用徽标，同时按“需处理”呈现，等待用户核查，避免新状态被误归类为运行中或完成。

团队卡片的状态优先级为：需处理 > 运行中 > 最近完成 > 未运行。成员可用性只作为提示，不自动替换 Lead、成员或评审角色。

Dashboard 的每条活动摘要固定回答四个问题：

| 问题 | 字段 | 示例 |
| --- | --- | --- |
| 谁负责 | `lead` / 当前任务成员 | `Kimi · 负责人` |
| 做到哪 / 最近回音 | `status` + `taskCounts` + `lastUpdate` | `并行核对 · 4/6 · ZCode 已开始实现（09:41）` |
| 下一步 | `nextAction` | `等待 ZCode 完成实现` |
| 结果在哪 | `runId` + `delivery` 证据入口 | `打开 Run · 查看 diff` |

## 5. 交互流程

### 用户主流程

用户进入团队入口后只需要沿一条主线操作：

```text
团队入口
  ↓
看 KPI：有没有运行中 / 需要处理的 Run？
  ↓
按「运行中」或「需处理」筛选
  ↓
选择最近活动或团队卡片中的一个 Run
  ↓
Run 详情
  ├─ 运行中：看阶段图和任务进度，等待实时更新
  ├─ 等待输入：回答问题，再点击「继续」
  ├─ 失败：查看 failure reason / error，决定取消或创建修订 Run
  └─ 已完成：查看交付证据、评审、验证和任务结果
  ↓
需要修改？创建修订 Run
  ↓
回到新 Run 继续观察
```

每一段都必须产生用户能看见的“回音”：

| 时点 | 必须出现的回音 | 没有回音时的处理 |
| --- | --- | --- |
| 请求发送后 | `已受理`、Run ID、负责人、首个检查点 | 显示排队/发送未知/失败原因，不显示假成功 |
| 阶段推进后 | 最近完成项、当前执行者、下一阶段、更新时间 | 显示“等待成员回报”，并保留刷新/进入 Run 入口 |
| 需要用户介入 | 等待原因、问题内容、可执行按钮 | 进入“需处理”筛选，不让任务停在无解释的 running |
| Run 终止后 | 完成/失败/取消/未知、结果摘要、验证、未完成项 | 显示核查或修订入口 |

### 三个关键场景

| 场景 | 用户看到什么 | 用户下一步 | 完成标志 |
| --- | --- | --- | --- |
| 发现运行 | KPI、筛选、最近活动、团队卡片 | 点击「打开 Run」 | 进入正确的 Run 详情 |
| 处理停靠 | 停靠原因、待决问题、结构化错误 | 回答/处理配置后点「继续」；无法处理则取消 | Run 状态重新进入运行中，或明确结束 |
| 确认交付 | Agent、评审、验证、阶段图、结果 | 查看结果；需要改动则「创建修订 Run」 | 结果可追溯，或新 Run 已创建 |
| 运行中观察 | 阶段图、任务状态、实时事件 | 等待；需要干预时暂停或取消 | Run 进入终态或等待输入 |

列表页的职责是「发现和分流」，Run 页的职责是「解释和操作」，原会话的职责是「查看完整过程」。三层之间不重复承担同一个动作。

### 打开团队工作台

1. 进入 `#teams` 后先显示工作台骨架，团队列表和右侧主区同时就位。
2. `/api/teams` 成功后并行拉取各团队 Run summary。
3. 所有摘要完成后更新 KPI、活动列表和团队卡片；单个团队读取失败只影响该团队的 Run 区域。
4. 保持当前筛选；从工作台打开聊天或 Run 后，浏览器返回回到原工作台和筛选状态。

### 运行筛选

- 「全部」显示所有团队；
- 「运行中」只显示至少有一个运行中 Run 的团队，并把最近活动限制到运行中状态；
- 「需处理」显示等待输入、暂停、失败、结果未知和新版本未知状态的团队；
- 筛选没有结果时提供「清除筛选」动作，不显示空白页面。

### 刷新与实时性

工作台可见期间每 15 秒刷新一次轻量 Run summary；离开工作台即停止轮询。手动刷新重新拉取团队和 Run 摘要。Run 详情继续使用现有 changes 订阅；完成、失败、取消、重连和 reset 都触发完整 detail 对账。

### 进入详情

最近活动行和团队卡片的最近 Run 都使用同一 `openRun(teamId, runId)` 入口。进入后不复制 summary 数据，直接以 Run detail 为权威，避免列表状态和详情状态发生两套解释。

## 6. 视觉与响应式

### 视觉方向

- 延续 Mobile / Bridge 当前米白页面、深绿主色和 Hanken 字体；
- 以平面分区、细边框和紧凑留白建立层级，避免堆叠大圆角卡片；
- KPI 使用等宽分隔的横向条带，状态使用稳定的左侧色线和徽标；
- 运行中使用主色，需处理使用警示色，失败使用错误色，完成使用低饱和绿色；
- 不添加渐变、装饰性大图或与团队数据无关的视觉元素。

### 布局尺寸

- 桌面端：沿用应用侧栏（当前宽度约 280px），主内容区滚动，Dashboard 内容最大宽度 1320px；
- 1024px：沿用应用现有侧栏断点，KPI 四列，团队卡单列，活动列表保留目标和进度；
- 720px 以下：Dashboard 沿用聊天详情的全屏模式和返回列表入口；聊天与团队列表共用同一组工作区切换，KPI 两列，团队卡单列；
- 390px：所有文字允许换行，操作按钮保持至少 44px 触控高度，长目标最多两行并显示省略号。

### 动效与可访问性

- 刷新按钮显示旋转状态，卡片和活动行 hover 只做轻微抬升；
- 筛选使用按钮组和 `aria-pressed`，状态徽标同时提供可读文本；
- 加载、刷新、错误和空状态使用 `role=status` 或 `role=alert`；
- `prefers-reduced-motion` 下移除过渡和脉冲；
- 不用颜色单独表达状态，所有状态同时显示文字。

## 7. 实现边界

实现涉及 `web/app.js` 的 `#teams` 路由和浏览器历史、`web/team.js` 的状态分组与管理操作、`web/presentation.css` 的桌面/移动工作区、`web/i18n.js` 的词条以及团队 UI 测试。当前 Run summary 已提供负责人、最近回音、下一步与交付投影，本次不改变后端 API 或 Run 状态机。

实现拆成五个小步骤：

1. 增加 summary 聚合、筛选状态和并行读取；
2. 重组 TeamsPanel DOM，加入 KPI、活动列表和团队网格；
3. 增加桌面/移动 CSS、骨架、错误和空状态；
4. 扩展服务端 Run summary 投影，派生当前负责人、最近有意义的 Run 事件、下一步和交付证据；
5. 在聊天与 Dashboard 呈现闭环字段，并用真实运行数据逐条验证受理、推进、停靠、终局四类回音。

不在本阶段引入图表库或新持久化事件类型；复用现有事件账本、Run 快照和交付投影。由于当前 Run 列表接口没有 lastUpdate/nextAction/currentOwner，必须扩展服务端只读投影，避免前端 N+1 拉取 Run Detail。
