## 1. 背景与目标

当前「团队」入口是一个窄弹窗，团队卡片按纵向重复排列。用户需要逐个展开 Run 才能知道：

- 有多少团队和成员；
- 哪些 Run 正在运行；
- 哪些 Run 等待处理或已经失败；
- 最近一次运行推进到了哪里；
- 进入详情后如何从阶段、任务、结果和错误继续排查。

本次目标是把入口改成一个团队运行工作台：先给全局状态，再给最近活动，再下钻到团队和 Run 详情。保留现有团队创建、聊天、Run、预算、定时、重命名和删除能力，前端复用已有接口，不改变后端编排语义。

完成后的首屏应该让用户在 3 秒内回答「现在有没有运行中的任务、哪里需要我处理、最近发生了什么」。

## 2. 参考结论

参考 `refs/multica/` 的 Dashboard、运行 transcript 和实时刷新实现，吸收以下做法：

- 页面先按范围组织信息，再用 KPI、趋势/活动和明细分层；
- 页面级筛选放在顶部，卡片级视图切换放在卡片内部；
- 运行状态、错误诊断、消息 transcript 分开建模；
- 任务消息按序合并，工具调用和结果按不透明 `call_id` 配对；
- 合并后再做 secret redaction，避免凭据跨分片被漏检；
- `task:completed`、`task:failed`、`task:cancelled` 和 reconnect 都触发刷新；
- 新增未知 failure reason 时保留原始值，客户端不把诊断信息静默丢弃；
- 空状态只在没有诊断信息时显示，失败任务优先显示结构化原因和错误。

这些原则与当前 Run 详情已有的阶段图、统计卡、任务卡和事件补读机制一致，Dashboard 只补入口层的信息组织。

## 3. 信息架构

团队弹窗升级为宽屏工作台，结构按下面顺序排列：

1. **页面头部**：团队运行标题、最近同步时间、刷新按钮、新建团队按钮。
2. **状态 KPI**：团队数、成员数、运行中 Run、需处理 Run。
3. **运行筛选**：全部、运行中、需处理；显示各筛选项数量，使用 `aria-pressed` 表达选中状态。
4. **最近活动**：最多显示 6 条 Run 摘要，按 `updatedAt` 倒序；每行显示状态、团队、目标、任务进度、更新时间，点击进入 Run 详情。
5. **团队网格**：桌面端两列，窄屏单列；每张卡显示团队状态、成员可用性、策略摘要、最近 Run 和主要操作。
6. **空状态**：没有团队、当前筛选无结果、Run 摘要读取失败分别给出原因和下一步操作。

Run 详情保持现有页面作为第二层工作区，信息顺序调整为：状态头部、停滞/等待提示、交付证据、统计、待决问题、动作预览、阶段图、任务列表。任务结果需要继续支持打开原会话、查看改动、工作区清理和诊断展开。

## 4. 状态与数据模型

Dashboard 只消费轻量 Run summary，不在团队列表中读取任务正文。首次打开和手动刷新并行请求：

- `GET /api/teams`：团队、成员、成员可用性和策略；
- `GET /api/teams/:teamId/runs`：目标、状态、更新时间和 `taskCounts`；
- 进入 Run 后继续使用现有 detail、`/stats`、`/graph` 和 changes 订阅。

客户端状态集合固定如下：

| 分组 | 状态 | 用途 |
| --- | --- | --- |
| 运行中 | `created`、`dispatching`、`collecting`、`reducing` | KPI、运行中筛选、活动排序 |
| 需处理 | `waiting_input`、`paused`、`failed`、`outcome_unknown` | 顶部提醒、需处理筛选、醒目错误色 |
| 终态 | `completed`、`failed`、`cancelled`、`stopped`、`outcome_unknown` | 进度归档和最近活动 |

任务进度统一由 `taskCounts` 派生：

```text
total = sum(taskCounts.*)
completed = taskCounts.completed
progress = total > 0 ? completed / total : 0
```

缺少 `taskCounts` 时显示「进度待同步」，不猜测为 0。未知 Run 状态保留原始字符串并显示通用徽标，避免新状态被误归类为完成。

团队卡片的状态优先级为：需处理 > 运行中 > 最近完成 > 未运行。成员可用性只作为提示，不自动替换 Lead、成员或评审角色。

## 5. 交互流程

### 用户主流程

用户进入团队入口后只需要沿一条主线操作：

```text
团队入口
  ↓
看 KPI：有没有运行中 / 需要处理的 Run？
  ↓
按「运行中」或「需处理」筛选
  ↓
选择最近活动或团队卡片中的一个 Run
  ↓
Run 详情
  ├─ 运行中：看阶段图和任务进度，等待实时更新
  ├─ 等待输入：回答问题，再点击「继续」
  ├─ 失败：查看 failure reason / error，决定取消或创建修订 Run
  └─ 已完成：查看交付证据、评审、验证和任务结果
  ↓
需要修改？创建修订 Run
  ↓
回到新 Run 继续观察
```

### 三个关键场景

| 场景 | 用户看到什么 | 用户下一步 | 完成标志 |
| --- | --- | --- | --- |
| 发现运行 | KPI、筛选、最近活动、团队卡片 | 点击「打开 Run」 | 进入正确的 Run 详情 |
| 处理停靠 | 停靠原因、待决问题、结构化错误 | 回答/处理配置后点「继续」；无法处理则取消 | Run 状态重新进入运行中，或明确结束 |
| 确认交付 | Agent、评审、验证、阶段图、结果 | 查看结果；需要改动则「创建修订 Run」 | 结果可追溯，或新 Run 已创建 |
| 运行中观察 | 阶段图、任务状态、实时事件 | 等待；需要干预时暂停或取消 | Run 进入终态或等待输入 |

列表页的职责是「发现和分流」，Run 页的职责是「解释和操作」，原会话的职责是「查看完整过程」。三层之间不重复承担同一个动作。

### 打开团队工作台

1. 弹窗打开后先显示头部、KPI 骨架和团队卡片骨架。
2. `/api/teams` 成功后并行拉取各团队 Run summary。
3. 所有摘要完成后更新 KPI、活动列表和团队卡片；单个团队读取失败只影响该团队的 Run 区域。
4. 弹窗保持当前筛选，不因刷新跳回「全部」。

### 运行筛选

- 「全部」显示所有团队；
- 「运行中」只显示至少有一个运行中 Run 的团队，并把最近活动限制到运行中状态；
- 「需处理」显示等待输入、暂停、失败和未知结果的团队；
- 筛选没有结果时提供「清除筛选」动作，不显示空白页面。

### 刷新与实时性

工作台打开期间每 15 秒刷新一次轻量 Run summary，手动刷新立即取消旧请求并重新读取。Run 详情继续使用现有 changes 订阅；完成、失败、取消、重连和 reset 都触发完整 detail 对账。关闭弹窗时停止轮询。

### 进入详情

最近活动行和团队卡片的最近 Run 都使用同一 `openRun(teamId, runId)` 入口。进入后不复制 summary 数据，直接以 Run detail 为权威，避免列表状态和详情状态发生两套解释。

## 6. 视觉与响应式

### 视觉方向

- 延续 Mobile / Bridge 当前米白页面、深绿主色和 Hanken 字体；
- 以平面分区、细边框和紧凑留白建立层级，避免堆叠大圆角卡片；
- KPI 使用等宽分隔的横向条带，状态使用稳定的左侧色线和徽标；
- 运行中使用主色，需处理使用警示色，失败使用错误色，完成使用低饱和绿色；
- 不添加渐变、装饰性大图或与团队数据无关的视觉元素。

### 布局尺寸

- 桌面端：团队弹窗 `min(94vw, 1120px)`，内容区最大宽度 1040px；
- 1024px：KPI 四列，团队卡两列，活动列表保留目标和进度；
- 720px 以下：弹窗接近全屏，KPI 两列，团队卡单列，活动行改为两行；
- 390px：所有文字允许换行，操作按钮保持至少 44px 触控高度，长目标最多两行并显示省略号。

### 动效与可访问性

- 刷新按钮显示旋转状态，卡片和活动行 hover 只做轻微抬升；
- 筛选使用按钮组和 `aria-pressed`，状态徽标同时提供可读文本；
- 加载、刷新、错误和空状态使用 `role=status` 或 `role=alert`；
- `prefers-reduced-motion` 下移除过渡和脉冲；
- 不用颜色单独表达状态，所有状态同时显示文字。

## 7. 实现边界

第一阶段只改 `web/team.js`、`web/style.css`，必要时更新 `web/index.html` 的静态资源版本号。后端接口、团队数据模型、Run 状态机和现有详情操作保持不变。

实现拆成四个小步骤：

1. 增加 summary 聚合、筛选状态和并行读取；
2. 重组 TeamsPanel DOM，加入 KPI、活动列表和团队网格；
3. 增加桌面/移动 CSS、骨架、错误和空状态；
4. 用真实运行数据验证打开团队、筛选、进入 Run、刷新和回到列表。

不在本阶段引入图表库、后端聚合接口或新的持久化字段。已有 Run 详情阶段图和统计卡继续作为深层视图，避免在入口重复实现一套图表。

- 刷新期间不出现重复卡片或滚动跳动；
