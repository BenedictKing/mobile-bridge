# 团队、Run 与编排交付

状态：现行特性基准。

## 1. 团队、成员与控制边界

团队绑定一个项目空间，成员引用真实 Agent 会话。`leadId` 和 `reviewerId` 分别确定主控与默认评审，可以由同一成员承担，但独立评审语义不能被自审替代。

1. 用户创建或打开项目默认团队，指定主控，再按需添加执行与评审成员。
2. 主控会话是用户可见的控制聊天；主控自我委派的具体工作在独立执行会话中运行，最终汇总回控制会话。
3. 成员引用失效时标记不可用，不静默改派到其他 Agent；更换默认评审等影响在途工作的操作受状态约束。
4. 删除团队只删除聚合关系和其运行记录，不删除成员原会话；存在未结束 Run 时拒绝删除。
5. 团队聊天沿用原会话的发送安全与幂等规则，但额外携带团队身份，不能误创建一条普通聊天任务。
6. 团队压缩主控另受活跃 Run 和待处理输入门控，详见[迁移与压缩基准](../session-migration-and-gateway-compaction.md)。

## 2. 团队输入与 Issue 路由

### 2.1 输入步骤

1. 用户从主控聊天或团队输入端点提交目标；持久队列入口先返回输入 ID 和 `queued`，不伪报已经创建 Run。
2. 输入正文、修订、内容哈希和团队内序号持久化；同 ID 同内容重放原结果，异内容拒绝。
3. 路由意图先落账，再幂等创建新任务、追加跟进或修订 Run；重启后按已存意图对账，不按当前活跃 Run 重新猜测。
4. 活跃 Run 数量、待路由容量和滚动派发预算超限时进入等待或背压，界面说明原因。
5. 多活跃 Run 需要选择归属时停在 `waiting_input`，由用户或明确规则决定。
6. 队列支持查看等待原因、编辑、取消和有版本校验的立即操作，旧页面不能覆盖新修订。

### 2.2 Issue 与 WorkItem

- Lead 通过结构化协议提出 Issue 创建、关联、忽略或澄清；原文区间由网关按 Unicode 精确解析，模型不自行计算位置。
- WorkItem 绑定来源输入、修订、原文范围、成员和审查策略；同一 Issue 可关联多条输入，同一输入也可拆成多个工作项。
- 归类协议错误进入有界修复；修复耗尽必须失败或等待人工，不能折叠成成功。
- Issue 状态由目标与证据投影决定，Task 全部结束不等于 Issue 自动关闭。
- 输入路由遵循既定公平与老化策略，不能因持续插入新输入让旧输入永久饿死。

## 3. Run、Task 与目标规划

### 3.1 执行流程

1. 输入路由创建 Run，确定成员、任务、依赖、收集策略和预算；显式 DAG 不得含环。
2. 主控通过 `<team-actions>` 提案派发、请求上下文或汇总；动作键、依赖和 `reviewOf` 由网关校验。
3. 每个任务先写派发事实和提交 ID，再进入消息队列；任务状态由真实派发、回合和对账证据推进。
4. 主控规划可把工作流、完成条件和评估反馈纳入协议；每批结束可触发有界目标评估。
5. 全部任务结束后进入汇总/收尾，结果回到主控控制会话；Run 最终进入完成、失败、取消、停止或结果未知等状态。
6. 暂停只停止后续调度，在途任务仍结算；终态 Run 不重开，修订通过带父 Run 的新 Run 完成。

### 3.2 状态口径

- Task `completed` 只表示该 Agent 任务正常结束；Task `outcome_unknown` 禁止自动改回 ready。
- Run `completed` 只表示执行与收尾完成，不等于需求全部达成。
- 目标结果独立表示未评估、待验证、待确认、部分达成、已达成或未达成，聚合时以最弱证据为准。
- 验证失败、目标未达成和执行结果未知是不同问题，不能共用一种“完成”提示。
- `waiting_input` 必须带原因和下一步责任主体，不能把所有等待都显示成“等待你回答”。
- 修订 Run 只在输入哈希一致时复用安全前缀；首次工作区写入后关闭依赖工作区状态的缓存。

## 4. 审查、验证与交付

1. 审查任务通过 `reviewOf` 绑定被审任务及依赖，不允许没有因果关系的“通过”覆盖执行事实。
2. 审查绑定派发时工作区指纹；后续写入使旧裁决标为 stale，但不篡改历史 verdict。
3. 无法解析工作区版本时停靠，不猜当前 HEAD；审查协议错误仅有有界修复机会。
4. 固定 argv 验证命令在任务终态且满足执行条件后运行，非零退出码形成失败证据并等待处理。
5. 交付卡分别展示 Agent 完成度、Review、Verify、待答问题和工作区信息；主控自然语言不能覆盖机器的 unknown、stale 或 failed。
6. 用户补充需求通过团队聊天形成新输入或修订；已移除的旧确认表单不得再作为当前交互写入文档。
7. 定时 Run 以触发 ID 对账，重启不得重复创建；通知失败不回滚已经落账的运行事实。

## 5. 工作区、预算与恢复

- 共享工作区使用跨团队写锁；独立 worktree 只引用用户已预备的工作区，不自动创建、合并或清理。
- 首次派发绑定基线；工作区丢失或基线漂移时停靠并报告，不自动重建或把未提交改动带入新目录。
- Run、团队和提供方并发限制分层执行；账号或权限错误只停受影响工作，不冻结无关任务。
- 预算按可归属的派发事实计量，不把无法精确归因的 token 当成团队预算；追加预算必须留下人工恢复记录。
- Team journal 是运行事实来源，快照可重建；重启按 journal、发送账本和会话证据对账。
- 输入哈希不一致、结果未知和工作区证据不足必须可见停靠，不能静默套用缓存或重复派发。
- 新增 Run/Task 持久字段时，必须同步事件应用、序列化、克隆和未知字段保留逻辑，确保 journal 重放不丢数据。

## 6. Swarm 与团队验收

Swarm 在团队设置中显式启用，且只影响新 Run：接受并冻结目标契约 → 生成候选产物与指纹 → 在独立副本执行固定命令评测 → 独立审查 → 处理冲突并集成 → 复验。修复和评测沿修订链累计预算，重复失败停靠。

本地快照不是操作系统沙箱；不支持安全执行的环境必须拒绝，自审、产物被改、同文件冲突或证据不足都不能放行。私有恢复账本不得通过公共事件流泄露。

验收至少覆盖：

- [ ] TeamInput 重试、重启路由对账、容量背压和编辑版本冲突。
- [ ] Run/Task 状态与目标结果分开，执行全部结束不会自动关闭 Issue。
- [ ] 暂停、恢复、取消、修订、预算耗尽和结果未知行为正确。
- [ ] Review stale、Verify failed、待答问题均不会被主控总结掩盖。
- [ ] journal 重建保留字段，工作区漂移不自动修复，定时触发不重复建 Run。
- [ ] Swarm 契约冻结、候选隔离、评测取消、独立审查和集成冲突符合边界。

详细状态见[团队运行图册](../team-runtime-diagrams.md)、[Run 结果契约](../team-run-outcome-contract.md)、[目标工作流](../team-goal-workflow-planning.md) 和 [Swarm 实施记录](../team-swarm-implementation.md)。
