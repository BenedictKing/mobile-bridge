# 团队、Run 与编排交付

状态：现行特性基准。

## 1. 团队、成员与控制边界

团队绑定一个项目空间，成员引用真实 Agent 会话。`leadId` 和 `reviewerId` 分别确定主控与默认评审，可以由同一成员承担，但独立评审语义不能被自审替代。

1. 用户创建或打开项目默认团队，指定主控，再按需添加执行与评审成员。
2. 主控会话是用户可见的控制聊天；主控自我委派的具体工作在独立执行会话中运行，最终汇总回控制会话。
   派活门槛：小范围修改、修复审查阻塞问题、需要与界面或调用方反复对齐接口的工作优先委派给 Lead 自己；只有接口已明确、可独立验收的整块实现或确需特定成员能力时才委派他人，且任务须写清接口约定、验收标准与需同步修改的同类位置。
3. 成员引用失效时标记不可用，不静默改派到其他 Agent；更换默认评审等影响在途工作的操作受状态约束。
4. 删除团队只删除聚合关系和其运行记录，不删除成员原会话；存在未结束 Run 时拒绝删除。
5. 团队聊天沿用原会话的发送安全与幂等规则，但额外携带团队身份，不能误创建一条普通聊天任务。
6. 团队压缩主控另受活跃 Run 和待处理输入门控，详见[迁移与压缩基准](../session-migration-and-gateway-compaction.md)。

## 2. 团队输入与 Issue 路由

### 2.1 输入步骤

1. 用户从主控聊天或团队输入端点提交目标；持久队列入口先返回输入 ID 和 `queued`，不伪报已经创建 Run。
2. 输入正文、修订、内容哈希和团队内序号持久化；同 ID 同内容重放原结果，异内容拒绝。
3. 路由意图先落账，再幂等创建新任务、追加跟进或修订 Run；重启后按已存意图对账，不按当前活跃 Run 重新猜测。
4. 活跃 Run 数量、待路由容量和滚动派发预算超限时进入等待或背压，界面说明原因。
5. 多活跃 Run 需要选择归属时停在 `waiting_input`，由用户或明确规则决定。
6. 队列支持查看等待原因、编辑、取消和有版本校验的立即操作，旧页面不能覆盖新修订。

### 2.2 Issue 与 WorkItem

- Lead 通过结构化协议提出 Issue 创建、关联、忽略或澄清；原文区间由网关按 Unicode 精确解析，模型不自行计算位置。
- WorkItem 绑定来源输入、修订、原文范围、成员和审查策略；同一 Issue 可关联多条输入，同一输入也可拆成多个工作项。
- 归类协议错误进入有界修复；修复耗尽必须失败或等待人工，不能折叠成成功。
- Issue 状态由目标与证据投影决定，Task 全部结束不等于 Issue 自动关闭。
- 输入路由遵循既定公平与老化策略，不能因持续插入新输入让旧输入永久饿死。

## 3. Run、Task 与目标规划

### 3.1 执行流程

1. 输入路由创建 Run，确定成员、任务、依赖、收集策略和预算；显式 DAG 不得含环。
2. 主控通过 `<team-actions>` 提案派发、请求上下文或汇总；动作键、依赖和 `reviewOf` 由网关校验。
3. 每个任务先写派发事实和提交 ID，再进入消息队列；任务状态由真实派发、回合和对账证据推进。
4. 主控规划可把工作流、完成条件和评估反馈纳入协议；每批结束可触发有界目标评估。
   目标评估及其协议纠错任务都绑定创建时的任务快照；纠错继承原评估快照并包含已创建的评估/纠错任务，已有任务不构成过期。快照之外新增执行任务时仍拒绝旧反馈，不得因纠错绕过过期校验。
5. 全部任务结束后进入汇总/收尾，结果回到主控控制会话；Run 最终进入完成、失败、取消、停止或结果未知等状态。
6. 暂停只停止后续调度，在途任务仍结算；终态 Run 不重开，修订通过带父 Run 的新 Run 完成。

### 3.2 状态口径

- Task `completed` 只表示该 Agent 任务正常结束；Task `outcome_unknown` 禁止自动改回 ready。
- Run `completed` 只表示执行与收尾完成，不等于需求全部达成。
- 目标结果独立表示未评估、待验证、待确认、部分达成、已达成或未达成，聚合时以最弱证据为准。
- 验证失败、目标未达成和执行结果未知是不同问题，不能共用一种“完成”提示。
- `waiting_input` 必须带原因和下一步责任主体，不能把所有等待都显示成“等待你回答”。
- 修订 Run 只在输入哈希一致时复用安全前缀；首次工作区写入后关闭依赖工作区状态的缓存。

### 3.3 Run 级只读协作协议

RunDetail 提供 `collaboration` 只读投影，把当前执行快照表示为一份 `team.md` 及对应的结构化数据。它用于统一展示团队目标、主控、实际参与成员和交接关系，不是新的调度输入。

1. 投影仅从当前 Team/Run/Task 快照派生；读取协议不得触发派发、唤醒、状态推进或成员变更。Lead 显式声明模式的持久化规则见 §3.4，不属于读取副作用。
2. `schemaVersion` 当前为 1，`revision` 使用 Run `version`。前端在 RunDetail 刷新后整体替换协议，不本地拼接增量事件，也不把旧 revision 当作当前计划。
3. `taskGoal` 来自 Run 目标，`orchestrator` 来自 Team `leadId`；`members` 只包含当前 Run 实际承担任务的非 Lead 成员，不把团队里未参与本 Run 的成员写入协议。Lead 只在 `orchestrator` 声明一次，即使没有单独执行任务也保留协调身份。
4. 成员关系使用稳定 `memberId`。`receiveFrom` 来自任务直接 `dependsOn` 的上游成员，`reportTo` 来自直接使用该成员任务作为依赖的下游成员；忽略自引用和不存在的任务引用，不从自然语言猜测交接。
5. 未显式声明模式时，协议包含多个参与者则标记为 `custom-dag`，只有一个参与者则标记为 `single-agent`；无执行任务的 Lead 仍计入协调参与者。这些观察值描述实际执行形状，不得把普通 DAG 猜测成五种声明式模式。`patternSource=observed-dag` 表示观察回退，`lead-declared` 表示采用 Lead 声明。
6. `rawMarkdown` 与结构化字段由同一次纯函数调用生成。文档中的显示名必须在本协议内唯一；名称重复时附加成员 ID，关系仍由服务端按成员 ID 计算。角色沿用 `lead`、`member`、`reviewer`，不把标签冒充本次任务职责。
7. Run 或 Lead 引用不完整时保留已知任务与成员关系，不虚构 Orchestrator；nil Run 不生成协议。数组字段使用空数组而非 null。
8. Run 页在阶段图后提供可折叠的协议视图，展示模式、来源、revision、成员职责与交接关系以及 `rawMarkdown`。旧网关没有 `collaboration` 字段时隐藏该视图，缺少 `patternSource` 时按观察投影展示，阶段图、任务卡和交付证据仍按原方式工作。
9. 该投影是展示协议，不是权限边界，也不要求 Agent 再次读取或遵守一份重复提示词。现有 `<team-actions>`、DAG、审查验证和完成判定仍是唯一执行事实来源。

### 3.4 Lead 显式声明协作模式

autoPlan Lead 可在 `<team-actions>` 顶层声明 `collaborationPattern`，把本次规划意图写入 Run；显式 Plan 仍以其 DAG 为事实，不通过该通道改写。

1. 可选值为 `classify-and-act`、`fan-out-and-synthesize`、`adversarial-verification`、`tournament`、`loop-until-done`。字段必须原样匹配，大小写、空白或其他值均拒绝；省略表示保留已有声明，不能用空串清除。
2. Lead 只在模式明确或需要修订时声明，不要求每个动作块重复。规划提示应说明：分类路由才用 `classify-and-act`，独立分支后合并才用 `fan-out-and-synthesize`，独立质疑才用 `adversarial-verification`，同题多候选择优才用 `tournament`，有明确质量门槛和退出决策者的反复修订才用 `loop-until-done`。单 Agent 能完成时不为形式而组队。
3. 非规划对象允许 `actions` 与 `collaborationPattern` 两个顶层字段；目标规划对象允许 `plan`、`actions`、`feedback` 与 `collaborationPattern`。非法模式与任一动作错误一样使整个动作块校验失败，不落声明、不执行动作，进入现有有界修复。
4. 合法声明与 Lead 任务终态、动作事实在同一个 `commitRun` 中原子提交。Run 持久化 `collaborationPattern`，并追加专用 journal 事件；后续合法声明采用 latest-wins，重复相同声明不重复写事件。快照损坏后的 journal 重建必须恢复最后一次声明。
5. 声明只表达规划意图，不强制拓扑、不创建额外任务、不唤醒成员，也不替代 `dependsOn`、`reviewOf`、独立审查或验证。实际执行与声明不一致时不得篡改任务事实来迎合标签；用户通过 `patternSource` 和阶段图分别查看意图与事实。
6. `BuildRunCollaboration` 优先使用合法持久声明，未声明的历史 Run 和新 Run 继续使用 §3.3 的观察回退。声明值进入 `rawMarkdown` frontmatter，revision 随同一 Run 提交递增。
7. 验收至少覆盖：五种值、非法值整块拒绝、空动作块声明、重复声明幂等、后续声明覆盖、Run 序列化与 Clone、journal 重建、旧 Run 回退，以及提示词和前端来源展示。

验收至少覆盖：扇出与汇总关系、重复成员名消歧、自引用和未知依赖、单成员 Run、nil Team/缺失 Lead、空数组、Markdown 与结构化数据一致，以及旧网关字段缺失时的前端回退。

## 4. 审查、验证与交付

1. 审查任务通过 `reviewOf` 绑定被审任务及依赖，不允许没有因果关系的“通过”覆盖执行事实。
2. 审查绑定派发时工作区指纹；后续写入使旧裁决标为 stale，但不篡改历史 verdict。
   审查协议把问题分为「阻塞问题」（必须写出具体触发场景，且影响正确性、数据、安全或验收条件）和「建议」；没有阻塞问题时裁决 passed，建议不构成返工理由。目标评估只针对阻塞问题派发返工，并要求返工补一条能拦住同类错误的测试或检查。
   同一 workflow 自最近一次用户输入（`input-` 控制任务）以来审查 failed 达到 2 次后，feedback 校验拒绝再为它派发返工，Lead 须以 blocked 列出剩余阻塞问题交用户决定；用户追加输入即重新授权，计数归零，其他 workflow 不受影响。
3. 无法解析工作区版本时停靠，不猜当前 HEAD；审查协议错误仅有有界修复机会。
4. 固定 argv 验证命令在任务终态且满足执行条件后运行，非零退出码形成失败证据并等待处理。
5. 交付卡分别展示 Agent 完成度、Review、Verify、待答问题和工作区信息；主控自然语言不能覆盖机器的 unknown、stale 或 failed。
6. 用户补充需求通过团队聊天形成新输入或修订；已移除的旧确认表单不得再作为当前交互写入文档。
7. 定时 Run 以触发 ID 对账，重启不得重复创建；通知失败不回滚已经落账的运行事实。

## 5. 工作区、预算与恢复

- 共享工作区使用跨团队写锁；独立 worktree 只引用用户已预备的工作区，不自动创建、合并或清理。
- 首次派发绑定基线；工作区丢失或基线漂移时停靠并报告，不自动重建或把未提交改动带入新目录。
- Run、团队和提供方并发限制分层执行；账号或权限错误只停受影响工作，不冻结无关任务。
- 预算按可归属的派发事实计量，不把无法精确归因的 token 当成团队预算；追加预算必须留下人工恢复记录。
- Team journal 是运行事实来源，快照可重建；重启按 journal、发送账本和会话证据对账。
- 输入哈希不一致、结果未知和工作区证据不足必须可见停靠，不能静默套用缓存或重复派发。
- 新增 Run/Task 持久字段时，必须同步事件应用、序列化、克隆和未知字段保留逻辑，确保 journal 重放不丢数据。

## 6. Swarm 与团队验收

Swarm 在团队设置中显式启用，且只影响新 Run：接受并冻结目标契约 → 生成候选产物与指纹 → 在独立副本执行固定命令评测 → 独立审查 → 处理冲突并集成 → 复验。修复和评测沿修订链累计预算，重复失败停靠。

本地快照不是操作系统沙箱；不支持安全执行的环境必须拒绝，自审、产物被改、同文件冲突或证据不足都不能放行。私有恢复账本不得通过公共事件流泄露。

验收至少覆盖：

- [ ] TeamInput 重试、重启路由对账、容量背压和编辑版本冲突。
- [ ] Run/Task 状态与目标结果分开，执行全部结束不会自动关闭 Issue。
- [ ] 暂停、恢复、取消、修订、预算耗尽和结果未知行为正确。
- [ ] Review stale、Verify failed、待答问题均不会被主控总结掩盖。
- [ ] journal 重建保留字段，工作区漂移不自动修复，定时触发不重复建 Run。
- [ ] Swarm 契约冻结、候选隔离、评测取消、独立审查和集成冲突符合边界。

详细状态见[团队运行图册](../team-runtime-diagrams.md)、[Run 结果契约](../team-run-outcome-contract.md)、[目标工作流](../team-goal-workflow-planning.md) 和 [Swarm 实施记录](../team-swarm-implementation.md)。
