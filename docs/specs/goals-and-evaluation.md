# Goal、计划与自动评估

状态：现行特性基准。

## 1. 工作模式与提供方路由

会话支持普通、计划和 Goal 三种工作模式。模式跟随当前聊天；补充运行中任务时沿用该任务模式，不能悄悄改成普通输入。

- **普通模式**：直接执行消息，可使用队列和 Agent 支持的 steer。
- **计划模式**：先形成计划；执行计划切回普通模式，填写修改意见后只能继续规划，不能忽略意见直接执行。
- **Goal 模式**：创建有持久状态的目标，按会话能力选择 native 或 gateway 提供方。

Goal 路由规则：

| 提供方 | 适用会话 | 执行与状态来源 |
| --- | --- | --- |
| Codex native | 本机 Codex | 受限原生 Goal 元数据接口 + 原桌面 owner 执行 |
| mcode native | MiniMax/mcode | Agent 扩展 Goal RPC |
| gateway | 其他支持的 ACP Agent | 网关持久状态机 + Agent 回合 + Jev 评估 |

SSH Goal、附件、排队创建和当前会话忙时的限制必须由前端与后端共同执行。网关托管 Goal 仅接受直接发送、无附件、长度受限的目标，同一会话只能有一个未结束 Goal。

## 2. 计划版本、批注与修订差异

计划审批在现有请求与回应协议上增加运行期修订投影，不新建持久化计划库或平行审批状态机。

1. ACP 计划优先使用 Agent 提供的稳定 `planId`，其次使用 `toolCallId`；两者都缺失时使用当前请求 ID，此时不臆造跨请求修订关系。每份计划包含 `planId`、从 1 开始的 `planVersion`、正文 SHA-256 `planHash`，修订时携带 `previousPlanContent`。
2. `plan_update` 与计划审批共享同一版本链。相同 `planId` 和正文的历史回放不增加版本；正文变化才递增版本并保留紧邻上一版正文。该投影只覆盖当前运行时，重启后不承诺保留完整计划历史。
3. 审批回应仍绑定原 pending request ID，并由现有命令账本保证幂等。前端展示或回传的版本字段不能替代请求身份，旧请求不能批准另一份计划内容。
4. 计划卡片显示当前版本和短内容哈希；存在上一版时可展开原始行级差异，显示增删统计并折叠长段未变更内容。差异过大时明确标记未精确对齐，不伪装成完整渲染差异。
5. 用户可在同一份计划正文内选中文字并引用到修改意见；跨计划、按钮和差异区域的选区不生成批注。带版本元数据的修订反馈包含 `Plan-ID`、`Plan-Version`、`Plan-SHA256` 和用户引用/全局意见，要求 Agent 处理全部意见且不得原样重交。缺少元数据的旧运行时保持原反馈文本和交互。
6. 新版计划需要新的待审批请求，旧版本审批不自动延续。批注与 Diff 只辅助人工决策，不触发自动批准、执行或额外网络请求。

## 3. Goal 创建与执行步骤

1. 用户选择 Goal 模式并提交目标；网关校验会话、提供方、长度、附件和现有目标。
2. 创建操作获得独立操作 ID 和目标修订号；重试沿用同一创建身份，后续恢复不得复用历史启动操作 ID。
3. 原生 Goal 先写元数据并读回确认，再由原 owner 发送启动回合；托管 Goal 先持久化目标，再认领启动派发。
4. 启动请求已经可能送达但结果不明时进入 `outcome_unknown`，不自动重发。
5. 每轮结束后，原生提供方读取原生状态；托管提供方以目标 ID、修订和回合 ID 绑定本轮评估。
6. 满足自动续轮条件时才派发下一轮；否则进入等待复核、等待输入、暂停、阻断或完成等明确状态。
7. 成功提交 Goal 后， composer 可恢复普通输入，但这不取消仍在运行的目标。

“目标已创建”“本轮已结束”和“目标已完成”是三个不同事实，界面不得合并描述。

## 4. 状态、人工控制与恢复

托管 Goal 的主要状态包括派发中、活动、评估中、等待输入、暂停、等待复核、阻断、结果未知、已完成和已取消；原生 Goal 以原生状态为准，但共享“未知结果不重放”的原则。

- 暂停和取消只阻止后续自动派发，不等于中断正在生成的 Agent 回复；立即停止必须使用独立停止操作。
- 修改原生 Goal 前必须暂停；原生修改重置统计并保留预算，托管 Goal 保留累计轮数与历史修订。
- 每次控制操作携带目标 ID、期望状态和修订号；旧页面或迟到评估不得修改新修订。
- “人工继续一轮”只授权一个新回合，不清空累计自动轮数；“标记完成”只在允许复核的状态开放。
- 网关重启后，未确认派发停在结果未知；执行中的托管 Goal 恢复为需要复核，而不是盲目续跑。
- 结果未知只能经用户核实和显式复核继续，界面不提供会重复启动目标的直接重试。
- 隐藏目标栏只改变显示，不暂停目标；新目标默认重新显示。

## 5. Jev 评估与自动继续

### 4.1 Goal 评估

1. 每个回合最多评估一次，输入包括目标、最近输出和停止原因。
2. 只有明确判断“尚未完成、可以安全继续”、正常结束且置信度达到阈值时，才自动派发下一轮。
3. 未配置评估服务、服务失败、低置信度、权限或额度问题都不得被解释为可继续。
4. 自动续轮有上限；达到上限后等待人工，不无限循环。
5. 评估结论绑定目标修订与回合，迟到结果不能推进新回合。

### 4.2 普通会话自动继续

- 回合落定后先运行确定性额度与停止原因检查，再由 Jev 判断是否意外中断和是否完成。
- Kimi `prompt.steered` 后的回合结束只是后台通知交接；后续 `trigger=notify` 回合与网关发起的原回合属于同一条逻辑任务链，不能按 `tool_use + completed` 重复续跑。
- 网关发起的 Kimi 任务链在原生存储追平并持续空闲至少 3 秒、且至少跨过两个原生轮询周期后，只执行一次完整结算；新 notify 回合、人工操作或新 prompt 取消尚未执行的旧结算。桌面原生回合和只读历史不自动继续。
- Jev 评估绑定被评估的回合与结算代次；提交前同步并校验最新原生状态。评估期间任务链变化、原生任务仍在运行或出现待答请求时，旧结论不得启动自动继续。
- 用户手动停止、有待答请求、原生 Goal 运行、存在排队消息或额度耗尽时，不自动继续。
- 无 Jev 配置时，仅允许对明确可恢复的中断使用保守规则，不能对正常未完成回复无限追问。
- 自动继续使用独立、可见且幂等的提交记录；连续预算与账号切换后的续跑预算分开计算。
- 任何人工消息、队列或审批操作都会重置相应自动继续状态。

## 6. 权限预判与隐私边界

Jev 同时服务于权限预判和目标评估，但两种决策不能混用：

- 权限预判只标注风险、可撤销性、置信度和建议选项，高风险优先展示。
- 自动审批必须同时满足建议一次性或本次会话允许、风险足够低、可撤销性与置信度达标；永久授权和其他请求仍需人工。
- 评估失败时回退人工与确定性标签，不根据猜测自动放行。
- Goal 评估只决定后续轮次，不把“任务未完成”当作权限批准依据。
- 目标、最近输出、请求上下文和 Jev 凭据的传输范围必须在设置中明确；未配置服务时不发起相关网络请求。
- Jev 配置和密钥以受限权限保存，接口只返回掩码；显式清除后不得被环境变量静默重新启用。

## 7. 验收标准与参考

- [ ] 普通、计划、Goal 模式在发送、补充和排队时不串模式。
- [ ] 相同计划回放不增加版本，正文变化递增版本并保留正确的上一版。
- [ ] 审批仍按 pending request ID 幂等回应，版本元数据不能串用或批准其他请求。
- [ ] 选区引用包含原文与当前版本信息，无元数据的旧运行时反馈保持原样。
- [ ] 计划 Diff 增删统计、长上下文折叠、超大内容降级和空内容边界正确。
- [ ] native 与 gateway Goal 路由正确，同会话不能重复创建活动目标。
- [ ] 创建、恢复和控制操作均幂等，旧修订与迟到评估不能覆盖新状态。
- [ ] 暂停、取消、停止、修改、人工继续和标记完成语义各自独立。
- [ ] Jev 未配置、失败、低置信度和结果未知均不会自动续跑。
- [ ] Kimi 连续 notify 交接不重复续跑，链尾未完成时能够评估并恢复，桌面会话不被接管。
- [ ] 迟到 Jev 评估不能推进新回合；提交前重新核验回合、结算代次、最新原生状态和待答请求。
- [ ] Kimi 去抖至少为 3 秒且至少跨两个原生轮询周期。
- [ ] 自动继续、切换续跑和人工操作分别遵守预算与重置规则。
- [ ] 自动审批只在全部安全条件满足时触发，永久授权始终需要人工。
