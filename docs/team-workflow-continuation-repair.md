# Team 续轮目标与任务派发语义修复

日期：2026-11-21。

## 实际失败

2026-11-20 23:31 的 `5b7d6c95-6889-44d2-9683-64c12320fff8` 是原 Run 的续轮，正文是一份计划完成说明。
运行服务已加载前次 `source=full` 与编排失败修复；此次没有格式错误，主控只输出 `ignore` Issue 块，既未派发也没有可读回复，随后 Run 完成。
原始 Run 的“按计划实现”目标仅保存在父 Run，派发上下文未提供该目标和实际交付记录；任务派发入口也只发送普通消息正文，未保留“要求执行”的语义。

## 修复

- Lead 控制续轮注入父 Run 链的目标、实际执行任务数量、最近可读结果和结束原因。`completed` 不再被提示为目标已交付。
- 最新指令优先；资料补充不自动撤销既有未完成目标。明确停止、改目标或新任务按最新指令处理，历史原文不参与本轮 Issue 来源区间。
- 血缘摘要限于同团队、最多 8 个前轮、最多 6000 rune；检测循环，截断保留头尾并明示缺失，避免丢掉目标末尾的执行要求。
- 普通对话的“交给团队”请求增加 `intent=task`。正文保持原样，意图分别持久化并进入幂等身份比较，重试不能把执行请求降级为普通沟通。
- 明确任务不得整条 `ignore`，也不能只建项、回复“收到”或提前 `summarize`；必须通过 `delegate` 派发工作，或给出明确的 `clarify` 与可读澄清。
- 普通沟通允许 `ignore`，但仍须有可读回复。非历史主控只返回机器块或空动作块时进入有界纠错，持续失败沿用失败终局。
- Lead 自己的独立执行任务完成后同样补控制会话交付，避免实质结果停留在执行会话。

## 回归

1. 多次状态更新后原始实现目标仍出现在派发内容中，首次派发冻结后重算不漂移。
2. 纯 `ignore` 块触发回复纠错，普通可读沟通可正常结束且不改写已成功归类。
3. 执行意图跨快照与 Journal 重放保留；同 ID 改意图冲突，非法意图被 HTTP 400 拒绝。
4. “计划已提交”任务：`ignore + 收到` 被拒；建项后只回复收到仍被拒；提前汇总代替执行被拒；修正后实际派发、等待成员结果并回控制会话交付。
5. 截断保留原目标末尾要求；Lead 自委派也生成最终交付。
6. 普通对话派发的正文、编辑草稿、幂等重试和当前聊天状态保持原契约。

测试使用隔离的 Go fake Agent 会话、实际 Team 调度/输入/队列代码，以及前端请求测试；不代表真实 movie-maker 实现已经完成。
