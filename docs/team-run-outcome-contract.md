# Run 执行状态与目标达成契约

> 状态：已实施；运行网关需用户重启后加载。2026-11-11。
> 依据：CCX Lean Run `11600089-3df6-47bb-b445-61ebd42ac378` 的实际结果与画布反馈。

## 1. 问题与完成边界

变更前 `FoldRunStatus` 按 Task 终态聚合，全部 completed 即候选 RunCompleted；仅配置了验证命令时才额外执行验证闸门。`teamIssueProject` 又把关联 Run 全部 completed 直接投影为事项 completed。本次保留执行状态机，取消后者的事项完成推断。

这证明的是编排执行结束，不能证明用户目标达成。自动规划可能遗漏要求、把实现降级成调查，或只给出替代方案；这些情况下所有 Agent 仍然可以正常结束。

CCX Lean 本次实际交付为调查报告与配置示例，明确记录“未修改文件、未运行运行时请求测试、未安排独立审查”。4 条任务分别为主控规划、调查、汇总和自动收口，4/4 不是 4 条用户需求的完成度。

每个目标先定义交付类型与完成条件，绑定原始输入及修订版本：

| 交付类型 | 完成条件示例 | 不能作为替代的材料 |
|---|---|---|
| 咨询回答 | 回答原问题、说明现有能力与限制、给出可操作步骤和依据 | 只有调查进度或“后续可以做” |
| 调查分析 | 已定位问题或明确调查边界，有可追溯依据与结论 | 将尚未验证的猜测表述为事实 |
| 实现修改 | 约定范围内的改动已产出，行为和所需检查满足要求 | 调查报告、设计建议或代码片段 |
| 操作执行 | 目标环境中的操作已执行，并取得约定结果凭据 | 只给操作步骤，或只在测试环境成功 |

原始输入有歧义时先澄清。Lead 可提出目标解释和验收条件，不能通过自行缩小范围使目标变成已达成；新增实质范围需要用户授权。

本例“如何添加过滤策略”可以按咨询回答处理，不能据此自动实施新功能。保守结论为“调查已结束，回答待确认”；若用户目标是实现组级白名单，则应为“部分达成：调查已交付，实施与验证未完成”。

采用一个 Run 执行状态、一份目标达成评估，以及各事项自己的目标范围。审查、验证、结果正文作为评估证据，避免再创建互相同步的重复状态机。

## 2. Run 执行状态

保留现有 `Run.status` 机器值作为执行生命周期，兼容现有调度和账本。界面明确标注“执行状态”：

| 机器值 | 展示 | 精确定义与出口 |
|---|---|---|
| created | 已受理 | Run 已持久化，等待调度；不是执行成功 |
| dispatching | 执行中 | 编排或成员任务仍在推进；具体成员按 Task 状态展示 |
| collecting | 收集结果中 | 兼容保留，当前主流程不写入 |
| reducing | 收口中 | 汇总或执行已配置的验证；详情区分两者 |
| waiting_input | 等待处理 | 受具体阻塞项影响，需要回答、审批、恢复账号、补证据或核查 |
| paused | 已暂停 | 用户主动暂停派发；在途任务仍可能结算 |
| completed | 执行结束 | 本轮调度成功收尾，结果已保存；不单独证明目标达成 |
| failed | 执行失败 | 已确认的执行错误，保留部分产物；不称为结果未知 |
| cancelled | 已取消 | 用户取消执行；不表示没有产生副作用 |
| stopped | 已停止 | 执行不再推进，记录原因；可恢复停靠沿用现有策略 |
| outcome_unknown | 执行结果待核查 | 是否发送或产生副作用尚不确定；禁止自动重发 |

`planning` 同样只保留兼容，不新增假运行阶段。现有恢复、重试与暂停语义继续适用，不能仅靠换中文标签改变调度。

`waiting_input` 必须返回 `reasonCode`、具体原因、责任主体和可执行动作；等待用户回答、等待审批、账号异常、验证失败和结果待核查不能共用“等待你回答”。

明确区分：没有证据确认发生了什么是 outcome_unknown；证据充分但目标未达成是目标评估不通过；验证命令失败是验证证据 failed。三者不能互相替换。

成员回合正常结束只足以支持 Task.completed。Run 还须处理未决动作、待答问题、必要收口与配置的验证闸门，才能执行结束。执行结束后仍可等待目标验证或用户确认，但不占用成员在途并发槽位。

历史终态 Run 不因“目标待确认”自动重开。继续执行通过新 Run 或明确修订，不能因刷新页面、等待确认或修改展示文案而重新调用 Agent。

## 3. 目标达成状态与证据

新增目标评估 `outcome.status`，与执行状态独立。它描述当前目标版本，不能从 Task 数量推导：

| 状态 | 展示 | 进入条件 | 下一步 |
|---|---|---|---|
| unassessed | 尚未评估 | 缺少目标条件或可用评估，包含未迁移的旧数据 | 明确目标、补充评估 |
| pending_verification | 待验证 | 已有候选结果，必要证据尚未取得或已经过期 | 执行具体检查并记录证据 |
| pending_confirmation | 待确认 | 已有可查看结果，仍有范围、语义或使用效果需要用户判断 | 展示结果与待确认点，接受反馈 |
| partial | 部分达成 | 已确认满足一部分条件，仍有未满足项 | 列出遗漏与后续工作 |
| satisfied | 目标已达成 | 目标条件全部满足且证据有效，必要确认已取得 | 展示结果与依据 |
| unsatisfied | 未达成 | 本轮结果不满足目标，且没有已确认的部分达成 | 展示原因、保留产物并提出修订 |

必要字段：`goalRevision`、`deliverableKind`、`criteria`、`resultRefs`、`assessedBy`、`assessedAt`、`reason`。条件项记录 stable ID、要求、met/unmet/unknown 判定及 `evidenceRefs`；不能只存一句“完成”。

实际模型：`Run.goals[scopeId]` 保存契约、逐项判断与操作去重记录，`goal_reviewed` 事件支持重放；API 的 `goalOutcomes` 提供逐目标视图，`outcome` 提供总体结论。事项以自身 ID 为 scope，未归类输入保留独立 scope，避免漏掉澄清中的要求。`scope.hash` 绑定原始输入和修订，`evidenceHash` 绑定本轮任务、回合、验证和未决问题。

当前采用保守判定：网关自动检查既有验证与审查事实，原始自然语言目标是否满足由用户逐项核对；模型正文不产生通过状态。用户可在结果评估前明确交付类型、追加条件及检查要求，已有条件不能删除，必要检查不能降级。确认全部满足时会再次核对必需检查的工作区指纹。

证据引用应绑定任务、派发 attempt、原会话、回合和产物版本。代码检查绑定工作区指纹，操作结果绑定环境；目标变更后旧确认只对旧版本有效。按派发记录追溯原会话，不能用成员当前绑定覆盖历史归属。

自动评估必须满足确定性条件：全部必要条件 met、交付结果可查看、无未决问题、无未确认执行副作用，且所有必需检查有效通过。模型的结论仅是评估建议，不能自己签发成功；模糊语义使用用户确认，不能靠关键词或置信分数猜测通过。

不要求每次咨询都运行构建或进行独立审查。每项检查的要求为 required/not_required/unspecified，执行结果另记 not_configured/pending/passed/failed/stale/unknown。not_required 必须有与任务类型相关的理由，unspecified 或 not_configured 不等于通过。已有 verdict=unknown 继续表示没有取得裁决。

咨询可在结果展示与必要确认满足后成为“回答已交付”；实现请求必须满足对应的改动与行为条件。未承诺上线时不要求上线，承诺上线时本地测试通过不能替代上线结果。

用户确认表示认可该目标版本的结果，不执行文件合入、部署或回滚。“不符合要求”保留结果并登记反馈；关闭事项也不回滚已产生的改动。这替代旧设计中无实际语义的“接受改动/丢弃改动”标签。

发生必需证据 stale 或目标修订时重新评估；历史评估保留，不能静默将旧 satisfied 用于新目标。部分达成、未达成或未知都不得显示全绿“已完成”。

## 4. 事项状态与界面口径

事项表示持续的用户目标，Run 表示一次执行。事项根据当前目标及其有效证据投影，不能把所有历史 Run 都作为必须成功的依赖；后续修订可明确替代旧失败结果。

| 事项状态 | 含义 |
|---|---|
| open | 目标已登记，等待处理或明确条件 |
| in_progress | 当前范围有执行、调查或验证正在推进 |
| waiting | 需要补充信息、证据或用户确认；必须显示原因和动作 |
| resolved | 当前范围全部满足，必要确认已取得 |
| closed | 用户明确结束追踪，不承诺目标已达成；保留关闭原因 |

partial/unsatisfied 是目标达成评估，作为事项的结果说明；执行异常则显示异常原因。没有后续执行时保持 open 或 waiting，不能因为所有 Run 终止就变成 resolved。

一个 Run 可覆盖多个事项；评估须按条件映射到具体事项，一个事项的成功不能自动关闭同 Run 的其他事项。自动标题也不能把“调查如何配置”扩成“实现配置能力”，再用调查结束来关闭它。

界面优先展示目标结论，并单独显示执行状态与结果摘要：

```text
按 Key 分组配置模型过滤策略
待确认 · 调查与方案已交付
执行：本轮结束 · Agent 任务 4/4 已结束
结论：现有能力为逐 Key 白名单与分组黑名单；分组白名单尚未实现
验证：运行时未验证 · 审查：未安排
下一步：查看回答，确认是否解决问题；需要新增能力时创建实现任务
```

4/4 只标注“Agent 任务执行进度”，包含规划和收口，不能称为“4 项需求已完成”或展示成目标达成 100%。没有可量化验收项时不显示需求完成百分比。

“待确认”必须能直接查看最终答案、确认本次答案是否满足问题或补充要求；“待验证”必须说明缺哪项证据。不得只有“需要人工处理”而没有可操作入口。只有 resolved 使用“已解决”，Run 详情则显示“执行结束 + 目标结论”。

画布、看板、Run 详情、聊天回音和通知消费同一份后端判定。最终结果优先引用本轮最终交付任务，不以每个 Task 的正文开头拼接代替答案；大结果保留完整入口与来源。

## 5. 迁移、实施与验证

此方案调整当前“Run 没有用户验收状态”的设计边界：加入目标条件与结果判定，不恢复已移除的 `deliveryStatus`，也不赋予确认按钮任何工作区副作用。现有机器状态继续表示执行，新增字段不能被旧客户端误当作执行命令。

已实施路径：

1. 统一保守展示：RunCompleted 显示“执行结束”；缺少目标评估的事项显示“结果待确认”，撤销“Task 全结束即事项已解决”的投影；所有页面和通知同步。
2. 建立目标契约：原始输入及修订自动绑定，用户通过目标表单明确交付类型、完成条件和验证要求。完整原始要求不可删除，已有条件不能事后缩小；当前不从 Lead 的自然语言回复自动生成或变更验收条件。
3. 补齐证据评估：优先展示最终收口结果，网关校验必要检查与版本，用户逐项核对语义条件后落 journal；证据不足保留待验证或待确认。不把模型声称成功自动转换为目标已达成。
4. 实现确认与修订：使用期望版本和操作 ID 幂等记录用户确认/反馈；目标评估、事项投影和回音从同一批持久事实更新。反馈进入后续修订，不改写历史成功或失败任务。
5. 新旧数据保守投影、确认幂等、证据失效与重放由回归测试覆盖；隔离实例通过真实页面验证部分达成、逐项确认、刷新与重启保留。运行中网关仍由用户决定并执行重启。

旧 Run 的 completed 仅迁移解释为执行结束；无结果时目标评估为 unassessed，已有可查看结果时保守投影为 pending_confirmation。不得批量重跑 Agent、补造验收证据或重新发送旧消息。目标评估变化使用新事件记录，旧事件保持原样。

旧 unknown 的恢复为独立前置：依据 task_dispatching 的会话、attempt 与 submission 定位原执行，不能依赖后来更新的线程绑定；核查得到迟到完成事实后重新评估，不能直接盖章目标达成。

关键回归场景：

- 本例 4 个 Task 全部结束，但只有调查与方案：执行结束，目标待确认，事项保持待处理。
- 用户明确要求实现，结果只含建议：目标不能 satisfied；部分条件已满足时为 partial。
- 纯咨询无需代码改动：不强加构建或审查；结果可读且原问题得到确认后可以回答已交付。
- 必需验证未配置、未执行、失败或过期；独立审查未取得裁决：各按真实原因阻止目标达成。
- Agent 正常结束但返回空内容、仅进度、遗漏子要求：执行事实不被篡改，目标不能自动通过。
- 发生执行异常或取消仍保留部分产物；未知副作用不被误标为确定性失败或自动重发。
- 一个 Run 包含多个事项；一个事项跨多个 Run；后续明确修订解决旧问题：按目标范围与有效证据评估，历史失败不永久拖住已解决事项。
- 原会话重新绑定、迟到回合到达、同文本重复发送、目标修订：凭派发身份和版本关联结果。
- 重复确认、过期页面确认、确认与新反馈并发、journal 写失败、重启：幂等、冲突可见且可重放。
- 手机与桌面的画布/看板/详情/通知给出同一结论，并提供查看结果和处理阻塞的入口。

验证分层：目标判定纯函数测试、API 与 journal 重建测试、前端投影测试、真实浏览器链路。隔离浏览器使用 CCX Lean 结果副本，所有确认写入隔离数据目录；真实 CCX 的目标确认记录未改写。

接口为 `POST /api/teams/:teamId/runs/:runId/goal-review`，action 为 define/assess/close。请求携带操作 UUID、Run version、goalRevision、scopeId、scopeHash 和 evidenceHash；define 追加完成条件，assess 逐项提交 met/unmet/unknown，close 记录停止追踪原因。接口不启动调度、不发送消息，也不合入、部署或回滚文件。冲突 409、非法目标或证据 400，错误直接显示在原表单。

兼容与回滚：新字段使用独立 schema 版本，保留旧 status 和旧事件可读性；回滚不得丢弃新增的确认事实。回滚展示仍使用“执行结束”保守口径，不能恢复“completed 即目标达成”的误导标签；已写文件与外部操作不随状态回滚。
