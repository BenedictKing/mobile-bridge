# 团队异步编排质量收敛与命令展示方案

> 状态：设计中；2026-11-08。本文是增量方案，未实施运行时代码。
> 依据：[多需求队列方案](team-demand-queue-plan.md)、[团队运行设计](team-orchestration-plan.md)、2026-11-08 代码审查和 [LangChain: Agents Are Going Async](https://www.langchain.com/blog/agents-are-going-async)。

## 1. 目标、现状与边界

目标是让 Lead 在成员执行长任务时仍能接收用户输入、知道哪些任务在途，并可靠地更新、排队或取消后续工作；同时让聊天时间线默认保持可扫描性，命令正文和输出按需展开。先保证输入账本和恢复正确，再扩大自动编排能力。

已实现：持久 TeamInput、机械路由、跨 Run 成员互斥和预算、`reviewOf` 版本绑定及 stale 投影。`docs/team-demand-queue-plan.md` 的阶段 0–5 标记不等于语义路由、多要求 WorkItem 拆分和工作项级审查策略全部完成。现有 `routeOneInput` 主要依据显式目标和活跃 Run 数量决定归属；Lead 的结构化路由提案尚未进入该路径。现有 Run/Task journal、提交队列、审批和通知应继续复用，不引入第二套 Agent runtime。

LangChain 文章的可借鉴机制是：主控与后台任务分离；启动后立即返回任务 ID；提供查询、更新、取消、列表；任务完成时通知主控；主控忙、闲、等待审批时都能正确接收结果；更新可选 `interrupt` 或 `enqueue`。这些是行为参考，不意味着直接引入 Deep Agents 或照搬其 API。

截图显示的期望是：折叠态只呈现“执行命令（状态）”，点击后才显示实际命令、输出和错误。仓库可控制的是移动 Web 时间线 `web/timeline.js`、`web/presentation.css` 及其投影；如果截图属于 Codex 桌面宿主自身的工具卡片，宿主界面不在本仓库控制范围，需将同一交互规范提交给宿主实现，不把 Web 修改误报为桌面生效。

## 2. 先收敛账本与恢复正确性

### 2.1 输入身份与隔离

当前 `InputLedger.Accept` 用全局 `inputs[inputID]` 查重，只核内容哈希。相同 ID、相同内容的跨 Team 请求可能返回另一个 Team 的输入；同 ID、不同内容则错误地按本 Team 的内容冲突处理。明确幂等身份为 `(teamId, inputId)`：可采用复合索引，也可先保持全局 ID 唯一并对 Team 不一致返回冲突；对外绝不能返回异 Team 记录。相应检查须覆盖 Get、操作 UUID 索引、快照重放和 API 投影，不只修 Accept 分支。上线前用双 Team 同 ID/同内容与不同内容的测试验证无串读。

`TeamInput.Clone` 当前只复制 `WorkItems`、`Revisions` 外层切片。补齐各 WorkItem 的 `TaskIDs`、`DependsOnItemIDs` 和各 Revision 的 `AttachmentIDs` 深拷贝，测试修改 Get/List 返回值不会改变账本或后续序列化结果。

### 2.2 路由意图是恢复依据

当前 `routeOneInput` 每轮重新按活跃 Run 推导目标，`MarkRoutingIntent` 接受 `routing` 状态下的新目标。若 Run/Task 已创建而 `input_routed` 尚未落账，重启或并发状态变化可能改派。`routing` 输入必须先读取已持久化的完整意图（类型、Run ID、Task ID、修订号和必要的父 Run ID），按原意图对账；不能因当前活跃 Run 变化覆盖。仅尚无 intent 的 `queued`/可重新规划的 `waiting_input` 输入才做新路由决策。已有意图无法完成时保留原因并待人工处置；明确撤销旧意图后才允许新目标，撤销本身须记事件。

`amend` 的父 Run 目前在落成时取 `RunsByTeam` 最后一项，必须在意图中固定父 ID，避免重泵时父血缘漂移。按“意图持久化 → Run/Task 幂等落成 → 路由确认”逐窗口注入故障，覆盖创建前、创建后确认前、确认后快照前，以及重启时活跃 Run 变化。断言同一输入至多一个当前执行归属、原父血缘不变、无孤儿 Task；`MarkRouted` 前校验目标 Task 确实存在且属于目标 Team/Run。

## 3. 主控与后台任务的异步协议

### 3.1 主控始终可达

TeamInput 的受理不等待成员任务结束：先持久化并返回 `inputId`，然后由路由器处理。Lead 不应把一次长成员调用当作自己的同步工具调用；网关持有 Task 生命周期，Lead 通过有界的在途任务摘要了解 `taskId/runId/workItemId/status/等待原因/最近事件序号`。用户可继续输入，主控将补充内容归类为纯问答、已有工作项修订、独立新工作项或需澄清的请求。分类仅生成可校验提案；网关校验来源片段、依赖、权限、容量、工作区和策略版本后才落意图。模型无法证明语义覆盖，涉及范围歧义或在途副作用时停靠给用户确认。

单条输入可拆成多个稳定 WorkItem，保留原文片段、约束和修订来源；一项要求不能静默丢弃。任务仍由现有 Run DAG 执行。先完成语义拆分与来源映射，再引入工作项级 `reviewPolicy=off/best_effort/required`；`required` 需要当前产物版本的有效通过裁决，`best_effort` 的未知/过期裁决必须如实展示。审查失败后的修复属于新任务和新版本，不能覆盖旧证据。

### 3.2 后台任务操作与事件

内部操作语义对应 `start/check/list/update/cancel`，但优先扩展现有 Team/Run/Task 接口，不平行复制任务账本。`start` 返回持久 Task ID 和受理状态；`check/list` 从 journal 投影读取；`update` 带操作 UUID、期望版本、目标 Task 和 `strategy`；`cancel` 是请求而非成功断言，须返回 `accepted/rejected/outcome_unknown` 等实际结果。所有操作有 Team 归属校验、审计事件和重放幂等。UI 必须区分“已受理更新”“已交付成员”“成员已完成”。

`enqueue` 把补充指令作为后继输入/Task，依赖原 Task 的终态；原任务继续执行。`interrupt` 只在适配器能确认停止、且工作区副作用可核对时采用：先记录中断意图和停止结果，再以新 attempt/Task 派发修订；停止结果未知时停靠 `waiting_input`，不得自动重发或宣称已取消。共享目录写锁、成员 lease、Team 预算和 `maxActiveRuns` 对两种策略照常生效。默认对一般补充用 `enqueue`；改变正在写入的目标时先提出中断选择，不由模型静默决定。

任务完成、失败、等待审批或等待输入后，用现有 journal 事件触发主控可消费的通知游标。主控忙时在下一次决策前读取新事件；闲时可唤醒一轮有界汇总；等待审批时保留原审批，不让完成通知替代用户答复。通知按事件 ID 去重、重启后按游标补读；通知投递失败不能回滚 Task 事实，也不能造成重复派发。子任务自己的审批在对应成员会话处理，Team 投影只关联和提示，不代替授权。

## 4. 命令执行行默认折叠

### 4.1 展示契约

折叠态一行显示 `执行命令（进行中/成功/失败/已取消/结果未知）`，由结构化 `status` 与 `exitCode` 映射；只有 `exitCode=0` 才是成功，缺失退出码不显示成功勾。失败保留醒目的状态图标和可访问文本，但命令、输出、错误正文仍需展开查看。点击标题或键盘 Enter/Space 展开；展开后保留原始命令、输出、退出码、截断/继续加载、复制能力。实时更新、分页、重连和语言切换不能意外展开或收起已打开的行；新行默认折叠。对审批卡不应用该规则，待批准命令必须保持可见以支持知情决策。

现有 `ChatTimeline.renderRow` 已用原生 `<details><summary>`，也保存重绘前的 `open`；CSS 的 `[data-tool]:not([open]) .activity-body` 已隐藏工具正文。截图对应的命令行仍露出三行预览，说明实际行未命中工具分类或来自仓库外宿主。实施时先用真实时间线数据确认 `role/kind/title/status/exitCode`，再把 `commandExecution` 等实际 kind 纳入明确的命令/工具分类，不依赖中文标题猜测。若真实 kind 已是 `toolCall`，应查明实际页面构建与 CSS 是否一致。对命令行使用独立 `data-command` 语义，避免把思考摘要和计划也一并隐藏；`row.text` 和 detail API 保持原样，不做数据删除。移动窄屏标题、长状态和焦点样式需验证。

### 4.2 验收

用固定 fixture 覆盖进行中、退出 0、非 0、取消、未知、长命令、多段输出、正文截断、实时状态变更和历史回放。断言折叠态没有命令/输出正文，也没有残留预览高度；展开后内容完整且可继续加载；失败状态折叠可见；审批卡仍显示待批命令。浏览器在桌面和手机视口截图，检查键盘操作及屏幕阅读器可识别的 summary。若目标是 Codex 桌面宿主，应另交宿主侧验收，不以仓库 Web 测试替代。

## 5. 实施阶段与验收

1. **质量闸门**：修复跨 Team 身份、深拷贝、路由意图和 amend 父血缘；增加崩溃窗口与并发测试。`go test ./internal/team ./internal/httpd`、race 测试、`go vet ./...` 通过；隔离数据目录重启后对账无重复归属。未通过不得扩大自动路由流量。
2. **命令展示**：采集实际行 kind 与构建版本，调整时间线分类/CSS/i18n；补 DOM 测试与桌面、手机浏览器检查。此阶段只改呈现，可单独回滚，不修改历史消息或审批卡。若页面来自宿主，形成独立需求并在宿主验收。
3. **主控任务可观测**：补稳定的在途 Task 列表、事件游标与完成通知；验证忙、闲、等待审批、重启和重复事件五种路径，确保主控不会因成员长任务失联。
4. **可控更新**：先上 `enqueue` 和用户可见的归属/等待原因，再上有停止确认的 `interrupt`。用真实适配器和隔离 Team 验证停止成功、失败、超时、未知及写锁竞争；未知结果不得自动重发。
5. **语义路由与审查策略**：Lead 提案、多 WorkItem 来源核对、超 Run 上限拆批、工作项级审查策略与失败修复回路。用“一条消息含两个独立要求和一个依赖审查”“进行中改变一个要求”“多 Run 目标歧义”验收无遗漏、无抢跑、无越权通过。

每阶段记录输入到交付的关联 ID、相关 journal 事件序列、测试结果与隔离网关实测。只在前一阶段验收后开放下一阶段；不以模拟 Agent 成功代替真实适配器验证。真实网关需要加载新后端或静态资源时，仅告知用户需要重启，不执行 `make restart`。

## 6. 兼容、回滚与开放问题

保留 `queueVersion:2` 与旧发送契约的分流；新增字段可选、旧客户端忽略。已有输入和 Run journal 只追加新事件，投影可重建；新功能均需显式开关与隔离 Team 验证。关掉语义路由时退回机械路由，已受理输入仍可查询和恢复；关掉任务更新时停止接收新更新，不抹除已落账的意图。命令折叠可独立回滚 CSS/分类，不影响服务端事实。

待实施前确认：截图究竟来自本仓库 Web 时间线还是 Codex 桌面宿主；真实命令行的 `kind` 和字段组合；哪些成员适配器能确认停止而不留下未知副作用；用户是否希望“纯问答”也走 TeamInput 账本。上述问题不阻碍阶段 1 的正确性修复与阶段 2 的仓库 Web 调查。
