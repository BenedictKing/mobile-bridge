# Kettu 学习、筛选与前端改造建议

> 状态：静态资源压缩、缓存、非首屏资源延迟加载与开发期静态检查已实现；其余产品能力均为未实施候选 · 调研日期：2026-11-23 · 参考项目：[KettuAI/Kettu](https://github.com/KettuAI/Kettu)，浅克隆于 `refs/Kettu`，commit `55fa4f8d84f884683a4647369a381a9df307a42b`。

## 1. 筛选结论

Kettu 的核心定位是桌面多 Agent 工作台；本项目的核心定位是手机继续已有会话，并通过 Jev、Goal、账号池和团队编排减少人工介入。两者不应按功能数量对齐。

本次保留以下原则：

1. 保留当前聊天对话列表，不增加全局“待你处理”中心，不因待确认请求改变现有最近交互排序。
2. 剩余人工请求继续在原会话卡片处理；列表只沿用现有待确认、运行、失败和未读标记。
3. Jev 已自动处理的低风险请求不需要再次吸引注意；重点是留下可核对的处理结果，而不是增加一层待办。
4. 优先改善自动化状态、少量人工卡片、长聊天阅读和静态资源交付，不追求 Agent 数量或桌面工作台功能覆盖。
5. Kettu 的 React、Electron、affectUI 和代码许可证均不构成迁移理由；只学习机制，不直接复制其 AGPL 或单独许可组件。

按当前项目收益排序，候选为：

| 顺序 | 候选 | 结论 |
| --- | --- | --- |
| 1 | 前端模块边界、静态检查、生产压缩与缓存 | 先做，和 Vue 解耦 |
| 2 | 自动化结果与人工回应的折叠审计记录 | 小范围补强现有卡片 |
| 3 | 多问题一次提交、计划修订差异、剩余人工卡片状态 | 按真实痛点实施 |
| 4 | 多条选区评论与侧聊 | 有明确使用场景后再做 |
| 5 | 跨 Agent 承接历史的按需读取 | 作为现有迁移链路的后续增强 |
| 6 | 端到端加密、设备会话恢复与备用链路 | 独立评估，不与 UI 改造捆绑 |

## 2. 与 Jev 对齐的交互候选

### 2.1 自动化结果只留证据，不制造新待办

可借鉴 Kettu 已回答卡片的折叠方式，但扩展为自动化审计：

- 区分“人工允许”“Jev 自动允许”“规则拒绝”“评估失败后转人工”，不把都显示成普通成功。
- 折叠后保留请求类型、目标、结果、时间和处理方式；展开才看风险、置信度、理由及原始 Diff。
- 自动继续、账号切换续轮和 Goal 续轮继续使用现有可见提交记录，不另建一套活动中心。
- 自动操作失败只更新对应会话和通知，不改变其他聊天顺序，不全局弹窗。
- 永久授权、高风险、低置信度和结果未知仍遵循现有人工或复核边界，不能为了低打扰而自动放行。

现行依据主要是 `docs/specs/goals-and-evaluation.md` 第 4–5 节；新增展示字段前需先补充该文档和聊天时间线基准。

### 2.2 少量剩余人工卡片仍值得打磨

- 多问题在一次提交前逐题编辑，允许跳过和自定义文本；秘密答案回答后不回显。
- 计划重新提交时显示相对上一版的增删，而不是重复阅读整份计划。
- 回应中禁用原卡片并原地显示错误；回应后保留折叠结果及回应设备。
- 默认主操作只选一次性、范围最小的允许，永久允许保持次级位置。
- 保留 Jev 风险与建议，不采用 Kettu 仅按 execute/delete 分类风险的简化规则。

这些是候选交互，不要求增加快捷键或全局收件箱；手机端优先保证触控、键盘和弱网反馈。

### 2.3 长聊天与输入细节

可选择吸收视口附近渲染、离屏跳过布局、流式输出期间选区接管滚动、草稿同时保存附件与评论、图片处理移入 Worker。每项必须先有性能测量和回归场景，不能为模仿实现而重写时间线。

## 3. 暂缓的 Kettu 能力

以下能力不进入近期需求：

- 全局 Needs you 页面、等待优先排序、九格分屏、桌面菜单栏和刘海常驻。
- 为追求数量新增低使用率 Agent；优先维护现有适配的协议和恢复质量。
- Marketplace、kettu.page 发布、Computer use 和完整移动设备控制台。
- 用 Kettu Workflow 替换现有 Team/Run。当前 DAG、独立审查、目标证据、工作区指纹和 journal 恢复应继续作为执行事实。
- 为视觉相似引入 affectUI 或直接复制 Kettu 源码。Kettu 为 AGPL-3.0，affectUI 有独立许可，本项目为 MIT。

可作为后续设计参考但不承诺实施：

1. Workflow 模板只作为现有团队的输入层；内容哈希变化后重新批准、每条返工边限次、人工复核点和明确阻塞原因值得复用。
2. 跨 Agent 切换复用现有迁移，不另建平行会话体系；未来可增加“保留首需求与最近轮次、省略部分按需读取”，并继续标明裁剪和来源。
3. 远程端到端加密应与既有 Blurt 研究合并评估。Kettu 的增量确认、请求水位恢复和备用连接可补充该研究，但不替换现有 HTTP 幂等与未知结果规则。
4. 原生 iOS 的锁屏回应等宣传能力未在本次仓库源码中核验，不作为已证实实现引用。

## 4. 前端：Vue 与资源压缩分开决策

### 4.1 改造前事实

- `web/` 没有包管理器或前端构建步骤，HTML 以全局脚本顺序加载 27 个自有 JS 文件。
- 自有 JS/CSS 合计约 1,070,193 字节；按当前服务端 gzip 级别逐文件估算约 323,583 字节，不含 vendor。
- `app.js`、`team.js` 和 `i18n.js` 分别为约 2384、2793、2301 行；主要风险是共享全局状态、隐式脚本依赖和缺少静态检查，不是缺少某个框架。
- 服务端已有动态 gzip，但静态响应统一为 `Cache-Control: no-store`，见 `internal/httpd/httpd.go:322`。因此版本查询参数并没有形成长期缓存，重复打开仍会重新传输资源。
- 当前 `go:embed` 直接嵌入原始 `web/`，见 `embed.go:6`；引入构建产物时需要明确源码、生产资源和测试所使用资源之间的关系。

### 4.2 决策

**暂不全量引入 Vue，也不把 Vue 当作压缩方案。** 框架运行时和重写成本不会自动减少加载量，反而可能把已经覆盖大量异常边界的会话逻辑变成回归风险。

第一阶段已采用更贴合单 Go 二进制的实现：Server 装配嵌入源码时一次性压缩 JS/CSS、生成哈希 URL 和预生成 gzip，并分别设置 HTML、旧地址与哈希地址的缓存策略。第二阶段增加统一延迟加载器，账号、Markdown/KaTeX 与 Dagre 只在对应入口加载，动态请求也使用同次装配的哈希 URL；保留团队列表所需模型脚本和经典全局/CommonJS 兼容层，没有为拆包改变列表行为。TypeScript 是锁定的开发期检查依赖，全部自有 JS 做解析检查，新加载器等已收敛文件通过 `@ts-check` 逐步纳入 `checkJs`，不进入 Go 构建或网关运行链路；未引入 Vue，也没有新的前端产物目录。

后续按与框架无关的四步推进：

1. **建立可比基线**：现有 Node 测试继续覆盖原接口，补充真实浏览器首屏、聊天切换、发送、审批和团队页面冒烟；记录生产包字节数与首屏请求数。
2. **收敛模块边界**：逐步改为显式 ES module 导入导出，配合 JSDoc/TypeScript `checkJs` 和 lint；不要求一次性把文件改名为 `.ts`。
3. **完善生产资源管线**：本轮已在 Server 装配期压缩 JS/CSS、生成内容哈希文件名并预生成 gzip；HTML 保持不缓存，哈希资源使用私有长期缓存，旧地址正确 revalidate。后续若比较 Brotli，必须先测量，不叠加无收益方案。
4. **按页面拆包和懒加载**：团队画布、账号、Markdown/KaTeX、Diff 等非首屏模块按需加载；先验证首屏和慢网，再决定是否继续拆。

只有新区域确实需要复杂响应式状态、组件边界能独立验证且实测收益超过运行时成本时，才考虑把该区域作为 Vue 岛屿接入。**不以 Vue 重写整个 `app.js` 作为第一步。**

## 5. 文档落点与实施门槛

本文只记录筛选和候选，不改变现行行为。`docs/specs/` 继续只描述已实现并接受的行为，不能把上表候选直接写成现状。

决定实施后按域更新：

| 需求 | 首先修改 | 需要写清的边界 |
| --- | --- | --- |
| 自动化结果与审批卡片 | `specs/goals-and-evaluation.md`、`specs/chat-and-timeline.md` | 自动/人工来源、失败回退、过期请求、历史可见性和隐私 |
| 多问题与计划修订 | `specs/chat-and-timeline.md` | 草稿、跳过、秘密答案、版本差异、重复回应 |
| 选区评论与侧聊 | `specs/chat-and-timeline.md` | 原文身份、消息更新后的定位、主会话上下文隔离 |
| 跨 Agent 按需历史 | `session-migration-and-gateway-compaction.md` | 转录预算、裁剪标记、历史工具权限、提示注入边界 |
| 远程加密与恢复 | `specs/connections-clients-notifications.md` 及 Blurt 设计 | 配对、撤销、重放、未知写入、备用链路和协议版本 |
| 前端生产资源 | `specs/deployment-data-reliability.md`、`ARCHITECTURE.md` | 源码/产物关系、缓存、嵌入、发布门禁和回滚 |

前端改造若被采纳，验收至少包括：

- [ ] 干净检出能够按标准命令生成同一份生产资源，嵌入网关后无缺失文件。
- [ ] 首屏不加载仅团队或账号页面使用的模块；所有延迟加载失败都有可重试反馈。
- [ ] HTML 更新能发现新哈希资源，旧页面不会因缓存混用不兼容版本。
- [ ] gzip 与未压缩回退正确，内容类型、CSP、Host/Origin 和登录行为不变。
- [ ] 真实手机或等效慢网记录首屏字节数、请求数和可交互时间，与改造前同场景比较。
- [ ] 现有 Node、Go、HTTP golden 和真实浏览器回归覆盖生产产物，而不只检查源码语法。
