# 移动端可靠性演进实施计划

> 状态：计划阶段 · 计划日期：2026-10-12
> 范围：审批幂等、竞态回归、通知对账、前台同步、`waiting_input`

## 1. 目标与约束

本计划把 OpenDots/OpenMuse 调研结论转化为 mobile-bridge 的五项可靠性改进，目标是让移动端在弱网、重复点击、网关重启和多入口并发下保持可解释、可恢复的状态。

实施约束：

- 保持现有 JSON 数据目录和客户端 API 兼容，避免引入数据库迁移。
- 所有外部副作用都必须区分 `accepted`、`rejected`、`outcome_unknown`。
- 自动审核、人工审核、桌面端审核统一进入同一个服务端决策入口。
- 先补持久状态和并发测试，再扩大 UI 与状态机范围。
- 不自动重试结果未知的审批或外部副作用。

## 2. 当前基线

已具备：

- `submissions.json` 的消息去重和原子替换写入。
- ACP 进程内 `handle.lock` 对 pending approval 的竞争保护。
- Jev 评估指纹、自动审核开关和审核详情展示。
- 完成通知的确定性去重键。
- SSE/轮询活动同步、移动端排队消息和审批卡。

已确认的缺口：

- 审批没有持久 receipt，重启后无法恢复执行边界。
- ACP 在调用回调前删除 pending，回调异常时结果无法判定。
- Jev 自动审核只用进程内集合去重，无法跨重启恢复。
- 完成通知缺少“已产生但尚未投递”的服务端对账记录。
- 前台恢复、乱序响应和读失败后的 UI 保留策略尚未统一。
- 缺少独立的 `waiting_input` 任务状态和恢复入口。

## 3. 总体决策

按四个阶段实施：

1. 审批 receipt、claim 和竞态测试。
2. 通知发布记录、启动/周期对账和补发测试。
3. 前台同步三件套及其浏览器回归测试。
4. `waiting_input` 状态、输入接口、恢复队列和移动端交互。

阶段之间保持可独立回滚。第一阶段完成后，后续阶段只能复用已稳定的状态与接口，不反向改变审批语义。

## 4. 阶段一：审批 receipt 与 claim 幂等

### 4.1 数据模型

新增独立的 `approval-receipts.json`，按 `thread_id + request_id` 索引。每条记录至少包含：

- `threadId`、`requestId`、`method`。
- `requestHash`：服务端保存的完整审批参数规范化哈希。
- `response`：已接受的决策内容；不接受客户端后续修改。
- `state`：`awaiting_review`、`claimed`、`accepted`、`declined`、`outcome_unknown`、`expired`。
- `createdAt`、`claimedAt`、`resolvedAt`、`source`。

receipt 写入采用现有的临时文件替换方式，并由独立锁保护。初始化时读取旧文件；损坏文件必须显式报错或安全降级，不能静默覆盖。

### 4.2 决策流程

`respond()` 先重新读取当前 pending request，校验 request ID、支持能力、过期状态和 `requestHash`，然后执行原子 claim：

1. 不存在 receipt 时创建 `awaiting_review`。
2. `awaiting_review` 只能被一个调用者迁移到 `claimed`。
3. 已有相同 response 的终态请求返回 duplicate 结果。
4. 已有不同 response 或不同 hash 时拒绝并要求刷新。
5. `claimed`、`outcome_unknown` 不允许自动重试。

人工响应和 Jev 自动响应只能竞争 claim，不能各自维护“已处理”集合。现有 `_auto_response_requests` 仅保留为进程内降噪，不承担正确性。

### 4.3 适配器语义

适配器在 claim 成功后再消费内存 pending。回调成功后写入 `accepted`，明确拒绝写入 `declined`；回调抛异常、超时或连接断开写入 `outcome_unknown`。只有确认桌面端返回结果后才从 UI pending 集合移除。

对于无法确认结果的 ACP 回调，不自动重放。用户需要通过刷新、桌面端核对或新的审批请求处理。

### 4.4 阶段一验收

- 同一 request 的双端并发只产生一次适配器回调。
- Jev 自动审核和人工审核并发时只有一个进入 claim。
- 相同 response 重试返回 duplicate，不再次调用桌面端。
- 不同 response、不同 hash、过期 request 都被拒绝。
- 回调异常保存为 `outcome_unknown`，重启后仍不可自动重放。
- 旧数据目录无需迁移即可启动。

## 5. 阶段二：通知发布与对账补发

### 5.1 持久发布记录

将完成、等待审批、等待输入等关键通知写入 `notification-outcomes.json`。记录使用确定性 key，例如 `task-done:<thread>:<turn>`，并保存通知类型、载荷摘要、产生时间、当前投递状态和最后一次尝试时间。

业务状态提交与通知记录写入必须先后稳定；任一投递失败都不能回滚业务结果。现有通知发送器继续负责渠道选择和渠道级去重。

### 5.2 对账循环

在 `_maintain()` 或通知模块中增加低频对账任务：启动时执行一次，之后每 60 秒执行一次。只扫描仍满足通知策略且未确认的记录，按确定性 key 重新发布。对账失败只记录并等待下一轮，不能阻塞会话维护。

完成通知已有记录的，迁移时只补齐缺少的发布状态，不重复发送已确认记录。

### 5.3 阶段二验收

- 在“业务结果已保存、通知尚未发送”之间模拟进程退出，重启后通知能补发。
- 同一通知经过实时发送和对账发送只到达一次。
- 用户关闭完成通知后，不会被对账循环重新开启。
- 无通知渠道、无订阅和已过期记录不会造成维护线程异常。

## 6. 阶段三：前台同步三件套

### 6.1 同步策略

在 `web/app.js` 的会话活动同步层统一加入：

- 页面从后台回到前台时立即刷新当前会话和列表。
- 每个资源维护单调递增的请求版本，旧响应到达时直接丢弃。
- 写操作成功后先保留成功状态；随后读取失败只显示刷新错误，不回滚已确认的本地状态。

当前 5 秒轮询周期保留，避免为了体验改动传输协议。SSE 连接恢复和轮询刷新共用同一个版本判定。

### 6.2 阶段三验收

- 标签页恢复后无需等待完整轮询周期即可看到最新状态。
- 人为制造响应乱序时，旧状态不会覆盖新状态。
- 写成功后模拟一次 GET 失败，成功提示、队列状态和审批提交状态仍保留。
- 登出、切换会话和语言切换不会复用旧请求版本。

## 7. 阶段四：`waiting_input` 任务状态

### 7.1 服务端状态

为需要用户补充信息的任务增加持久状态记录，最小字段包括任务标识、问题列表、已完成 checkpoint、创建时间和过期时间。任务进入 `waiting_input` 时暂停执行并产生通知；不会把问题伪装成普通聊天消息。

新增输入入口：

- `GET` 返回当前待补充问题及任务摘要。
- `POST` 校验问题版本、字段完整性和长度，成功后保存答案。
- 提交成功后通过 CAS 将任务恢复为 `queued`，由现有维护循环重新调度。

同一输入请求重复提交应返回 duplicate；问题版本已变化时拒绝并要求刷新。任务取消、过期或结果未知时不得恢复执行。

### 7.2 移动端交互

复用审批卡布局和排队消息动作，展示任务摘要、缺失字段、过期时间和恢复状态。提交后立即显示“已提交，等待恢复”，后台刷新负责确认最终状态。

### 7.3 阶段四验收

- 缺上下文任务能暂停并在重启后保持 `waiting_input`。
- 合法补充信息只恢复一次。
- 重复提交、过期提交、字段不完整和任务已取消均有明确错误。
- checkpoint 在恢复前后保持一致，不能从任务起点重复执行已确认副作用。

## 8. 测试矩阵与验证顺序

每个阶段完成后先运行聚焦测试，再运行全量测试：

1. `python3 -B -m unittest tests.test_bridge tests.test_jev tests.test_notification_activity -v`
2. `python3 -B -m unittest discover -s tests -v`
3. `npm run test:desktop`

新增测试按层次放置：

- `tests/test_approval_receipts.py`：哈希、状态迁移、重复和过期。
- `tests/test_bridge.py`：Bridge 与适配器的并发、重启和未知结果。
- `tests/test_notifications.py`：发布、补发和渠道去重。
- `tests/*.test.cjs`：前台恢复、乱序响应和 `waiting_input` 卡片交互。

所有并发测试使用 `threading.Barrier` 或事件同步，不使用固定 sleep 作为正确性条件。涉及时间的测试注入 clock 或使用可控时间戳。

## 9. 发布、兼容与回滚

每个阶段使用独立 conventional commit。提交前检查数据文件权限、临时文件替换和旧版本读取行为；不执行 `git push`。

兼容策略：

- 新 JSON 文件不存在时按空状态启动。
- 老的 `notification-completions.json` 和 `submissions.json` 保持原格式可读。
- 新状态字段采用向后兼容的默认值。
- 客户端暂不认识新状态时显示通用“需要处理”，服务端仍保留完整状态。

回滚策略：

- 阶段一回滚前保留 receipt 文件，旧版本只会忽略它，不删除它。
- 阶段二停止对账线程不会删除已发布记录。
- 阶段三可单独关闭前台立即刷新和请求版本判定。
- 阶段四只在明确启用任务输入能力的任务上产生新状态，旧任务路径不受影响。

## 10. 非目标

- 本轮不引入 SQLite、Redis 或新的消息队列。
- 本轮不把所有普通聊天消息改造成任务状态机。
- 本轮不实现推送渠道扩展或原生移动端重写。
- 本轮不自动重试 `outcome_unknown` 的外部副作用。
- 本轮不为纯 UI 重构增加新的状态管理框架。

## 11. 总体验收标准

计划完成后必须满足：

- 审批的正确性不依赖单进程内存锁。
- 网关重启不会丢失关键通知或把未知副作用自动执行第二次。
- 移动端回前台、弱网乱序和读取失败都有稳定行为。
- 用户补充任务上下文后可从 checkpoint 恢复，且恢复操作幂等。
- 聚焦测试、Python 全量测试和桌面端测试全部通过。
- 每项变更都有对应的验证记录和可回滚提交。
